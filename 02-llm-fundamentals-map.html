2.1

What an LLM Actually Is

Backbone
next-token predictionstatelessnesscontext windowknowledge cutoffhallucination
Mental modelA very good autocomplete you steer entirely through what you put in the context. It has no memory and no live knowledge — only the text in front of it, right now.

Given text, the model predicts the most likely next token, appends it, and repeats. Three consequences drive everything in agent design: it's stateless (you resend the whole conversation every call to fake memory), it has a finite context window (input + output tokens it can consider at once), and it will hallucinate confidently past its knowledge cutoff. Agents exist largely to feed the right context in and check the output.

Misconceptions to unlearn
  • "It remembers our chat" — no; your app resends the history every call.
  • "It knows today's news" — only up to its training cutoff, unless you supply the data (that's what RAG & tools are for, Step 3).
  • "A confident answer is a correct one" — fluency ≠ accuracy; always verify facts it asserts.

2.2

Tokens

Backbone
sub-word chunks~4 chars / tokeninput + output pricingtoken counting
Mental modelTokens are the model's currency and its memory budget — you pay per token and the context window is measured in them.

Tokens are sub-word chunks (~4 English chars, ~0.75 words). You're billed per input + output token, and every limit is in tokens. This governs cost, context budgeting, and later your chunking strategy for RAG.

Common mistakes
  • Non-English text & code tokenize less efficiently — more tokens per character.
  • A long system prompt is re-billed on every call — trim it or use prompt caching (2.8-ish, Step 6).
  • Guessing length by characters — count tokens before sending to stay within limits.

2.3

The Messages API

Backbone
system / user / assistantmulti-turnstop_reasoncontent blocks
Mental modelA conversation is just an array you keep appending to and resending — the API call itself is stateless.

Three roles: system (instructions/persona), user, assistant. A multi-turn chat is a list of messages you resend each call. Read stop_reason to know why it stopped (end turn, max tokens, tool call). A message's content is a list of blocks, not a string — text, tool calls, thinking, images and documents all arrive as typed blocks, so always check block.type before reading .text.

from anthropic import Anthropic
client = Anthropic()                       # reads ANTHROPIC_API_KEY from env (1.6)

msg = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=4096,                       # room for thinking AND the answer
    system="You are a terse assistant.",   # system is separate on Anthropic
    messages=[{"role": "user", "content": "Name 3 primes."}],
)
# content is a LIST of blocks -- never assume content[0] is text
print("".join(b.text for b in msg.content if b.type == "text"))
Common mistakes
  • On Anthropic the system prompt is a top-level param, not a message in the list.
  • Reading msg.content[0].text blindly — with thinking on, block 0 is often a thinking block and this raises.
  • Forgetting to append the assistant's reply before the next user turn drops the "memory".
  • Assistant prefill is gone. Putting a partial assistant turn last to force a format returns a 400 on current models — use structured output (2.6) or a system instruction instead.

2.4

Effort & Thinking · rewritten 2026

Backbone · the most out-of-date topic online
effort: low→maxadaptive thinkingmax_tokensstop_sequences✗ temperature✗ top_p✗ budget_tokens
Mental modelYou no longer tune randomness. You tune how hard the model thinks — and you steer style with the prompt, not with a dial.

This module is the single most stale topic in every LLM tutorial online, and getting it wrong is a hard error, not a quality issue. Current models (Sonnet 5, Opus 5, Opus 4.7/4.8) return a 400 if you set temperature, top_p, or top_k to a non-default value. The replacement is effort: low / medium / high / xhigh / max, passed inside output_config. It controls how much the model reasons before answering — which is the knob that actually moves quality now.

Adaptive thinking is on by default. That has a consequence people trip over constantly: max_tokens caps thinking and the answer together, so a budget copied from an older tutorial silently truncates your output mid-sentence.

# WRONG on current models -- this raises a 400
msg = client.messages.create(model="claude-sonnet-5", temperature=0, ...)

# RIGHT
msg = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=4096,                          # thinking + answer share this
    output_config={"effort": "high"},         # low | medium | high | xhigh | max
    messages=[...],
)
DrillRun step2_first_call.py, then add temperature=0 back to the classify() call and run it again. Read the 400 carefully — that error message is the one you'll hit every time you paste code from an older blog post.
Common mistakes
  • Copying temperature=0 from any pre-2026 tutorial — 400. Just delete the argument.
  • Using thinking={"type":"enabled","budget_tokens":N} — also 400. Use {"type":"adaptive"}.
  • max_tokens=1024 carried over from an older model — now truncates, because thinking eats the same budget.
  • Reaching for effort:"max" everywhere. high is the default and usually the sweet spot; low is right for cheap subagents and rerankers.
  • Expecting reproducibility. temperature=0 never actually guaranteed identical output — if you need determinism, pin it with structured output and evals, not a sampling knob.

2.5

Prompt Engineering

Applied · the highest-ROI skill here
system promptsfew-shot exampleschain-of-thoughtXML tagsbe specificgive it an "out"
Mental modelYou're not commanding the model — you're arranging the context so the answer you want is the most likely continuation.

The core levers: a clear system prompt (role, rules, tone); few-shot examples (show, don't just tell); chain-of-thought ("think step by step" before answering hard problems); and XML tags to delimit input for Claude (<document>…</document>). Be specific, and give the model a legitimate "I don't know" path so it doesn't invent one.

DrillTake one vague prompt ("summarize this") and rewrite it with a role, 2 few-shot examples, an explicit output format, and an XML-tagged input block. Compare the two outputs side by side.
Common mistakes
  • Vague asks → vague output; specificity beats politeness.
  • Negative-only instructions ("don't be verbose") work worse than positive ("reply in ≤3 bullets").
  • Examples that contradict your instructions confuse the model more than no examples.

2.6

Structured Output

Applied
tool use / function callingJSON modeinput_schemavalidate the result
↩ builds on 1.3 · Pydantic
Mental modelDon't parse prose — force the model to fill a schema, then validate it right back into your Pydantic model.

Reliable JSON comes from tool use: you pass a schema, the model returns input matching it. This is the exact seam that connects to Step 1 — your Pydantic model_json_schema() becomes the tool's input_schema, and the response validates straight back with model_validate.

# reuse WeatherQuery from Step 1.3:
tools = [{
    "name": "save_weather",
    "description": "Store a weather query",
    "input_schema": WeatherQuery.model_json_schema(),   # 1.3 -> tool schema
}]
# ...model replies with a tool_use block; validate its input straight back:
q = WeatherQuery.model_validate(block.input)            # typed + guaranteed valid
Common mistakes
  • Asking for JSON in prose instead of using tool/structured mode — far less reliable.
  • Trusting the returned JSON without validating it (1.3, 1.4).
  • Schema too loose (Any fields) → the model fills them with junk.

2.7

Streaming

Applied
SSEtoken-by-tokendeltasasync for
↩ builds on 1.2 · Async
Mental modelConsume the response as an async stream of events, not one blob — this is where Step 1's async for pays off.

Streaming sends the response token-by-token over SSE, so users see output immediately instead of waiting for the full generation. You accumulate deltas into the final text — and later, into partial tool-call JSON.

aclient = AsyncAnthropic()                 # the ASYNC client -- 1.2 for real

async with aclient.messages.stream(
    model="claude-sonnet-5",
    max_tokens=4096,
    messages=[{"role": "user", "content": "Write a haiku about latency."}],
) as stream:
    async for text in stream.text_stream:  # 1.2: consume incrementally
        print(text, end="", flush=True)
    final = await stream.get_final_message()   # usage/stop_reason live here
Common mistakes
  • Streaming from the sync client and calling it async practice. If it isn't async with / async for, you're still blocking a worker for the whole response.
  • Tool-call arguments arrive as partial JSON while streaming — accumulate before parsing.
  • No error handling mid-stream — and note you cannot turn a mid-stream failure into a 500, because the headers are already sent. Failures must be delivered inside the stream (see step6_service.py).
  • With thinking on, the default is to stream empty thinking blocks — to a UI that looks like a long pause. Pass display:"summarized" if you show reasoning.

Providers & Model Choice · new

Applied · portability + the interview question
BedrockVertex AIFoundrygateway / LiteLLMmodel tierscost per 1Mdata residency
Mental modelThe model is a dependency, not a fact of nature. Centralise which one you call and where you call it, exactly like a database connection string.

The same Claude model is reachable through Anthropic's API, Amazon Bedrock, Google Vertex AI, and Microsoft Foundry. The request body is essentially identical; only the client constructor and the credential source change. This matters far more than it looks: enterprise and government work almost never calls api.anthropic.com directly — it consumes AI through a procured platform, inside a chosen region, under an existing contract. If your only skill is one vendor's SDK, you are not portable to the jobs that exist.

The other half is choosing a model, which every interviewer asks. There is no "best" — there is a cost/latency/quality triangle. Right-sizing is the biggest cost lever you have: a cheap model for routing, classification and reranking, a mid model for the workhorse path, a top model only where correctness genuinely pays for itself.

# samples/config.py -- one place, so a platform move is a one-line edit
PROVIDER = os.environ.get("AI_PROVIDER", "anthropic")

if PROVIDER == "anthropic":  return anthropic.AsyncAnthropic()
if PROVIDER == "bedrock":    return anthropic.AnthropicBedrockMantle(aws_region=...)
if PROVIDER == "vertex":     return anthropic.AnthropicVertex(project_id=..., region=...)
# ...every one of these exposes the SAME .messages.create() surface
DrillOpen samples/config.py. Compute the cost of a 50-turn agent conversation at each of the three price tiers in PRICES, then decide which tier each of the samples in this repo should actually use. That arithmetic is most of "cost engineering."
Common mistakes
  • Hardcoding a model string across dozens of files. When it's renamed — and they are renamed — you're grepping under pressure.
  • Assuming model ids are portable: Bedrock prefixes them (anthropic.claude-sonnet-5), Vertex uses bare or @-versioned ids.
  • Assuming features are portable. Newer capabilities land on the first-party API first; check availability before designing around one.
  • Comparing token counts across model generations — tokenizers change. Re-count against the model you're actually shipping.
  • Defaulting to the biggest model "to be safe." That's a 5–10× bill for work a cheaper tier does identically.

Documents & Images · new

Applied · the highest-volume real workload
document blockimage blockbase64Files APIcitationsconfidence gate
Mental modelA PDF is just another content block. Document AI is not a separate discipline — it is structured output (2.6) with a file glued to the front of the message.

If you ship one useful AI thing at work, it will probably be this: "read these thousands of forms and give me structured data." Scanned submissions, invoices, certificates, screenshots — this is the bulk of real enterprise AI demand, and it is genuinely easy. You put a document block (PDF) or image block before your text instruction and validate the result into a Pydantic model. No OCR pipeline, no layout parser.

The engineering is not in the call — it's in knowing when not to trust it. The model will always return a confident-looking object. Ask it for a confidence field and route anything low to a human. That one branch is the entire difference between a demo and a system people are allowed to rely on.

file_block = {"type": "document",          # "image" for png/jpg
              "source": {"type": "base64",
                         "media_type": "application/pdf",
                         "data": base64.standard_b64encode(pdf_bytes).decode()}}

r = client.messages.parse(                 # constrains AND validates
    model=MODEL, max_tokens=4096,
    output_format=InspectionRecord,        # a Pydantic model (1.3)
    messages=[{"role": "user", "content": [file_block, {"type": "text",
               "text": "Extract this form. Do not infer missing values."}]}],
)
record = r.parsed_output                   # already an InspectionRecord
DrillRun step2b_document_extract.py, then point it at a real PDF of your own: uv run step2b_document_extract.py my_form.pdf. Now deliberately feed it a document that's missing a field and watch what confidence does — that behaviour is the thing you're actually building on.
Common mistakes
  • Putting the instruction before the file. Models follow the instruction better once they've seen the data.
  • Trusting the output because it's well-formed. Schema-valid and factually right are different properties — that's what the confidence gate is for.
  • Base64-ing a huge scan on every call. Use the Files API to upload once and reference by id across requests.
  • Downsampling away the detail you need — or the opposite, sending needless high-res pages and paying ~3× the image tokens.
  • Forgetting a document is untrusted input. Text inside a PDF can carry a prompt injection straight past your input guardrail (6.4).

One real, single-shot LLM feature

No agent loop yet — just one great call that exercises the whole step end to end.

A script that makes ONE real API call and:
  • sends a system + user message                        (2.3)
  • with effort + max_tokens set deliberately            (2.4)
  • using a few-shot + chain-of-thought prompt            (2.5)

Then a SECOND script that:
  • sends a PDF or image as a content block               (2.9)
  • returns a validated record, not prose          (2.9 ↔ 2.6)

That's a working, production-shaped LLM feature. Step 3 wraps this single call in a loop and hands the model tools — and that loop is an agent.
