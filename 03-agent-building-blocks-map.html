3.1

The Agent Loop

Backbone · this IS the agent
while loopplan → act → observestop_reasontool_result feedbackmax iterations
Mental modelAn agent is Step 2's single call in a while-loop: call the model → if it asks for a tool, run it and feed the result back → loop → stop when the model is done.

Everything else in this step (tools, RAG, memory) exists to feed this loop. The crucial inversion from a normal program: the model decides what to do next; your code just executes and reports back the observation. Get this loop right and you've built an agent — the rest is quality.

messages = [{"role": "user", "content": task}]
for _ in range(MAX_STEPS):                         # 3.6: always cap iterations
    reply = call_model(messages, tools=TOOL_SCHEMAS)   # Step 2 call
    messages.append(reply)
    if reply.stop_reason != "tool_use":
        break                                      # model gave a final answer
    for call in reply.tool_calls:
        try:
            result = TOOLS[call.name](**call.input)    # 1.1 dispatch
        except Exception as e:
            result = f"ERROR: {e}"                  # feed the error BACK, don't crash
        messages.append(tool_result(call.id, result))  # the "observation"
DrillBuild this loop against your Step 2 call with one real tool (a calculator). Log every step. Confirm the model calls the tool, sees the result, and then answers.
Common mistakes
  • No iteration cap → an agent that loops forever, burning tokens and money.
  • Not feeding tool errors back — the model can often recover if it sees what went wrong.
  • Dropping the assistant's tool_use turn from history — the next call breaks.

3.2

Tool Use / Function Calling

Backbone
input_schematool_use / tool_resultdispatchparallel tools
↩ builds on 1.3 + 2.6
Mental modelA tool = a Pydantic schema + a Python function. The model picks one and fills the args; your code runs it and returns the observation.

Tools are how an agent affects the world — search, query a DB, call an API, run code. The model never executes anything; it emits a structured request (from your 1.3 schema) and you run the real function and hand back the result.

Common mistakes
  • Prompt injection: tool results & retrieved text are untrusted — they can carry instructions that hijack the agent. The risk is born here; full defenses in Step 6.4.
  • Side-effecting tools (write/charge/delete) with no idempotency or confirmation.
  • Returning huge tool outputs that blow the context window (3.5).
  • Vague tool descriptions — they're prompts; the model chooses tools based on them.

3.3a

Retrieval — Grounding in Your Data

Backbone
lexical (BM25)embeddingshybrid searchchunkingretrieve → injectpgvector / Chroma
Mental modelDon't bake facts into the model — find the right chunks at query time and paste them into the context.

Retrieval solves 2.1's cutoff + hallucination problem: fetch relevant text, inject it, and the model answers from your data. Start lexical. A keyword ranker like BM25 needs no embeddings, no database and no index-time pipeline — and on many corpora it is most of the way there. Add vectors when you can point at the queries lexical search demonstrably cannot serve (see 3.3b). Hybrid — run both, merge the scores — beats either alone and is the sane production default.

# stage 1: cheap, wide recall (lexical, and/or vector)
candidates = bm25(question, k=20)

# stage 2: narrow precision -- rerank the few, not the corpus
best = rerank(question, candidates)[:4]

prompt = f"Context:\n{best}\n\nQ: {question}"   # inject, then call the model
Common mistakes
  • Reaching for a vector DB first. It's the most expensive fix and rarely the first one you need.
  • Chunks too big → noisy & costly; too small → context lost. Tune it against a labelled set, not by feel.
  • Different embedding model at index vs query time → garbage matches.
  • Retrieval quality caps answer quality — bad retrieval, bad answer, full stop. Most "hallucination" bugs are this.
  • Letting permissions leak: if a user can't read a document, retrieval must not surface it. Filter before ranking, not after.

3.3b

Retrieval Quality · new

Applied · where the real wins are
recall@klabelled queriesrerankingcandidate poolcitations
Mental modelGrade the retriever separately from the agent. Otherwise you cannot tell "the model lied" apart from "the model never saw it."

This is the module that pays for itself. Write ten labelled queries — question → the doc ids that should come back — and measure recall@1 and recall@3. Suddenly "our RAG feels bad" becomes three separate, named problems with three different fixes: not ranked first (add a reranker), not retrieved at all (add vectors or fix chunking), retrieved but ignored (fix the prompt). Almost nobody does this, which is exactly why saying you do lands in an interview.

Then make the answer checkable. Have the agent cite which chunk each claim came from. A grounded answer with citations is auditable by a non-expert; an ungrounded one has to be trusted.

DrillRun step3b_retrieval.py. It scores three retrievers against 12 labelled queries and prints the table. Read which queries each one fails and why — then add two queries of your own that break it.
Common mistakes
  • Only measuring the final answer. That hides whether retrieval or generation is at fault.
  • Expecting a reranker to fix recall. It reorders the candidate pool — it cannot conjure a document the pool never contained.
  • A candidate pool too small to rerank. Retrieve ~20, rerank down to ~4.
  • Tuning on the same queries you evaluate on. Keep a few you never look at.
  • Never growing the set. Every real retrieval miss in production should become a labelled case.

3.4

Memory

Backbone
short-term (history)long-term (store)summarizationretrieval memory
Mental modelShort-term memory is the message list you resend; long-term memory is just RAG (3.3) over your past interactions.

Because the model is stateless (2.1) with a finite window (2.2), you engineer memory: keep recent turns verbatim, summarize or store older ones, and retrieve relevant past facts when a new turn needs them.

Common mistakes
  • Unbounded history → context overflow and steadily rising cost.
  • Summarizing away detail you later need — keep the source retrievable.
  • Treating memory as magic — it's the same retrieve-and-inject mechanics as RAG.

3.5

Context Management

Applied
window budgetingtruncationcompaction / summarizerelevance filtering
↩ builds on 2.2 · Tokens
Mental modelContext is a budget you actively manage every turn — not an infinite bucket you keep pouring into.

Every token costs money and eats the window. Inject only what's relevant this turn, trim or summarize old turns and stale tool outputs, and watch the size of a growing system prompt. Good context management is often what separates a flaky agent from a reliable one.

Common mistakes
  • Dumping whole documents instead of retrieved chunks (3.3).
  • Keeping every stale tool output in context forever.
  • Ignoring that a long system prompt is re-billed on every single call.

3.6

Guardrails & Recovery

Applied
max iterationstool-error feedbackoutput validationhuman-in-the-loop
↩ builds on 1.5 · Retries
Mental modelAssume every tool can fail and the model can err — the loop must either recover or stop cleanly.

Production agents need iteration caps, validation of tool args & outputs (Pydantic, 1.3), errors fed back so the model retries (3.1), and human approval gates before anything destructive or irreversible.

Common mistakes
  • Silent infinite loops with no step cap or cost ceiling.
  • Trusting tool output blindly instead of validating it.
  • No kill-switch / confirmation for destructive actions (deep dive in Step 6).

The capstone — proof you've cleared Step 3

A real agent — no mocks

Take your Step 2 capstone and turn it into an agent that actually does things.

Build an agent that:
  • runs an ASYNC tool-calling loop with a step cap  (3.1, 3.6, 1.2)
  • has 2 real tools — e.g. a search tool + calculator (3.2)
  • runs parallel tool calls CONCURRENTLY, returning
    every result in ONE user message                  (3.2, 1.2)
  • answers from a retrieval store you built yourself (3.3a)
  • keeps recent turns + summarizes older ones         (3.4, 3.5)
  • feeds tool errors back so it can recover           (3.6)

Then ask it a multi-step question that needs
a retrieval AND a tool call AND reasoning to answer.

Then, separately, SCORE the retriever on its own:
  • 10 labelled queries, recall@1 and recall@3       (3.3b)
  • compare naive vs BM25 vs BM25-plus-reranking     (3.3b)

If it retrieves, calls a tool, sees the result, and reasons to a correct answer — you've built a working agent. If you can also say how good its retrieval is, in a number, you're ahead of most people who claim this skill. Steps 4–6 make it easier to build (frameworks), bigger (multi-agent), and safe to ship (production).

Why async, specifically? Step 1 called async the non-negotiable core, and this is the file where that becomes true. A synchronous agent loop blocks a whole worker for every second the model is thinking — so one user at a time. Make the loop async here and Steps 5 and 6 get concurrent workers and a streaming endpoint for free; leave it synchronous and both need thread-pool workarounds.
