5.1

When to Go Multi-Agent

Backbone · the gate question
single vs multiindependent subtasksseparation of concernsN× cost
Mental modelDefault to one agent. Go multi only when subtasks are genuinely independent, need different tools/context, or the work can't fit one context window.

Multi-agent multiplies cost, latency, and failure modes. Justify it with a real reason: parallelizable fan-out, specialized roles that shouldn't share a prompt, or context that exceeds a single window. Absent that, a single agent with good tools (Step 3) is simpler and more reliable.

Common mistakes
  • Going multi-agent for prestige when one agent would do.
  • N agents = N× tokens & latency — the bill compounds fast.
  • Errors propagating across agents with no isolation or checkpoint.

5.2

Orchestration Patterns

Backbone
prompt chainingroutingparallel fan-outorchestrator-workersevaluator-optimizer
Mental modelAn orchestrator decomposes the task, workers run in parallel, the orchestrator synthesizes — the same fan-out/gather shape as 1.2, one level up.

The canonical patterns: chaining (sequential steps), routing (classify → send to a specialist), parallelization (fan-out + vote/merge), orchestrator-workers (dynamically split subtasks), and evaluator-optimizer (generate → critique → refine). Most real systems compose a few of these.

Common mistakes
  • Synchronous barriers that waste the parallelism you paid for.
  • No dedup/merge of overlapping worker output.
  • Orchestrator context bloating as it accumulates every worker's full result.

5.3

MCP — Model Context Protocol

Backbone · consume it (★★) · author it (○)
open protocolservers / clientsruntime discoverytools · resources · promptsstdio / remote
Mental modelMCP is USB-C for tools — one open protocol so any agent (Claude, IDEs, your app) can use any tool or data source without bespoke glue per integration.
The position this track takes, so you don't get mixed signals: consuming MCP servers is worth a solid ★★ and about an hour — it's genuinely useful and it's the part employers mean when they mention MCP. Authoring a server is a ○ "know it exists" until you have something specific to expose; the API is small and you'll learn it in an afternoon on the day you need it. Read the client sample, skim the server sample.

Instead of hand-wiring each tool into each agent, tools and data are exposed once as an MCP server; any MCP-capable client consumes it. The part that surprises people is runtime discovery: your client calls list_tools() and hands whatever comes back to the model. Your agent gains capabilities it was never coded against — which is the entire payoff of a standard, and something you should see happen once with your own eyes.

DrillRun step5b_mcp_client.py. It launches mcp_dorm_server.py as a subprocess, discovers its tools, and uses them — with no tool schemas written in the client. Then add a third tool to the server and re-run the client unchanged.
Common mistakes
  • Conflating MCP tools with in-process functions — MCP is a protocol boundary, with a process and a serialization cost.
  • Ignoring auth & trust of remote MCP servers (Step 6 security). A third-party server sees every argument you send it.
  • Treating tool descriptions from a remote server as trusted text — they land in your prompt, so a hostile server is an injection vector.
  • Over-exposing capabilities — grant least privilege per server, and keep write tools behind an approval gate (6.7).
  • Writing a server when you needed a function. If nothing else will ever consume it, a protocol boundary is pure overhead.

5.4

Evaluation

Backbone · replaces "it feels right"
eval setassertionsLLM-as-judgerubricsrefusal casesregression
Mental modelYou can't improve what you don't measure — swap vibes for a dataset of tasks graded on every change.

Build a set of representative tasks + expected outcomes; grade with assertions or an LLM-as-judge; track pass rate across prompt/model/tool changes. Non-negotiable once an agent does anything non-trivial — and the foundation for the CI gate in Step 6.

Use the cheapest grader that can do the job. A substring or JSON assertion is free, instant, and never flakes — use it whenever the right answer contains a specific fact. Reserve the LLM judge for what assertions genuinely cannot express, and give it a rubric written as a pass condition, not a description of the task. A suite that is mostly deterministic runs in seconds and you'll actually keep running it.

The cases people forget are the refusals. Ask about a record that doesn't exist. The correct answer is "I don't know" — and no substring check can express "must not invent a number." Those cases are where an agent's real reliability lives, and they're the first thing a careful interviewer probes.

DrillOpen evals.py. Eight cases use a free substring check; four use the judge — including two where the agent is supposed to refuse. Now break the agent on purpose: delete the "say so plainly rather than guessing" line from the Step 3 system prompt and re-run. Watch which cases flip.
Common mistakes
  • Evaluating on the very examples you tuned the prompt on.
  • Judging everything with an LLM. It's slow, costs money, and adds variance where a substring check would have been exact.
  • A vague rubric ("is the answer good?"). Write the pass condition explicitly, and tell the judge to fail when uncertain.
  • Trusting an LLM-judge without ever checking its agreement with a human on a sample.
  • Only testing the happy path — no refusal cases, no malformed inputs, no "the tool returned an error" cases.
  • A suite that never grows. Every production failure should arrive back here as a new case.
  • Gating CI at 100%. Judge-graded suites have real variance; a perfect bar flakes and gets disabled within a week.

5.5

Subagents & Handoffs

Applied
delegationcontext isolationreturn contract
Mental modelA subagent is a fresh context you hand a scoped task — it returns a result, not its entire transcript.

Isolate noisy subtasks (deep research, verification) into subagents so the main context stays clean (3.5). Define precisely what's handed in and what comes back — the return contract is where multi-agent systems succeed or turn to mush.

Common mistakes
  • Passing entire histories instead of a scoped task + inputs.
  • Losing a subagent's work when it dies with no result captured.
  • Vague return contracts → the orchestrator can't use the output.

5.6

Shared State & Communication

Applied
message passingshared storerace conditions
↩ builds on 1.2 · Concurrency
Mental modelPrefer explicit message passing over shared mutable state; if agents must share state, guard it like any concurrent system.

Agents coordinate by passing messages or through a shared store. Concurrent writes cause the same races you learned to tame in 1.2 — keep contracts explicit, and bound the chatter so cost doesn't spiral.

Common mistakes
  • Unsynchronized writes to shared state → corrupted or lost updates.
  • Agents deadlocking while each waits on the other.
  • Unbounded back-and-forth chatter inflating cost with no progress.

The capstone — proof you've cleared Step 5

An orchestrated, interoperable, measured system

Build an orchestrator that:
  • fans out to 2–3 workers CONCURRENTLY       (5.2, 1.2)
  • each worker has its own tools + scoped task (5.5)
  • synthesizes worker results into one answer  (5.2)
  • is scored by a 12-case eval suite with a
    reported pass rate                          (5.4)
  • uses cheap assertions where it can, and a
    rubric-driven judge where it must           (5.4)
  • includes at least 2 REFUSAL cases the agent
    is supposed to decline                      (5.4)

And separately, a client that:
  • connects to an MCP server over stdio        (5.3)
  • DISCOVERS its tools at runtime rather than
    hardcoding any schema                       (5.3)

If your orchestrator delegates, merges, and you can quote a pass-rate number that includes refusal cases — you can build and measure real multi-agent systems. Step 6 makes it safe to put in front of users.

Notice how small the orchestrator is. In step5_orchestrator.py the whole thing is one gather() and one summarizing prompt. That is not a simplification for teaching — that genuinely is what most "multi-agent frameworks" are wrapping. Which is exactly why 5.1 tells you to default to one good agent: the pattern is cheap to reach for and expensive to run.
