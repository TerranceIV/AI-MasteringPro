6.1

Observability & Tracing

Backbone · non-optional in prod
traces / spanstoken & cost loggingLangSmithLangfuseHeliconeOpenTelemetry
Mental modelAn agent without traces is undebuggable — capture every model call, tool call, and decision, with tokens, latency, and cost attached.

Multi-step, non-deterministic systems fail in ways plain text logs can't explain. You need per-step inputs/outputs and a full trace of a run to see why the agent went sideways. Tools: LangSmith, Langfuse, Helicone, or OpenTelemetry-based stacks.

Build one by hand before you buy one. A span is just: a request id, a start time, a counter per model call, token totals, and a computed dollar figure — emitted as one JSON line. Do that once and every vendor dashboard becomes legible, because you'll know exactly which field each chart is reading. The number that surprises everyone: one user question is many billable model calls, because the loop re-sends the whole history each turn. Cost per question is the metric that matters, and you cannot see it without this.

Drillstep3_agent.py takes an on_usage callback; step6_service.py turns it into a trace line. Run the service, ask one question, and read the JSON: model_calls will be greater than 1. Now ask a question needing two tools and watch the cost move.
Common mistakes
  • Logging prompts with PII/secrets — mask them first (6.7), or your trace store becomes the leak.
  • No per-call cost attribution, so you can't find the expensive step.
  • Logging prose instead of structured JSON, so nothing can be aggregated.
  • Counting one request as one model call. In an agent loop it never is.
  • Sampling so aggressively you never capture the rare failure you're chasing.

↩ builds on 2.2 + 1.2
Mental modelRight-size the model per step, cache the static prefix, batch what isn't latency-sensitive, stream what a user waits on.

Use a small/fast model for easy steps and a big one only for hard reasoning; prompt caching slashes cost + latency on repeated context (2.2); the Batch API is cheaper for offline work; streaming (2.7) improves perceived speed; parallelize IO (1.2).

Common mistakes
  • Using the biggest model for every step "to be safe" — burns budget.
  • Re-sending an uncached fixed system prompt on every call.
  • Serial tool/model IO that could have run concurrently.

Guardrails & Safety

Backbone
input validationoutput filteringmoderationhuman-in-the-loopleast privilege
↩ builds on 1.3 · Validation
Mental modelValidate what goes in and what comes out — never treat model output as safe-to-act-on by default.

Constrain and validate inputs, filter/moderate outputs, gate risky or irreversible actions behind human approval (3.6), and give each tool the least privilege it needs. The model is a capable but untrusted component in your system.

Common mistakes
  • Acting on tool/model output with no validation step.
  • Handing an agent broad, unscoped tool permissions.
  • No moderation on anything user-facing.

6.4

Security

Backbone · the #1 agent threat
prompt injectiondata exfiltrationleast privilegesandboxing
Mental modelTreat all retrieved, tool-returned, and user content as untrusted — it can carry instructions that hijack the agent (prompt injection).

The top agent risk is prompt injection: malicious text inside a web page, document, or tool result that redirects the agent — potentially exfiltrating data through its own tools. Defenses: least-privilege tools, sandboxing code execution, never mixing untrusted content with high-privilege actions, and confirming consequential actions.

Common mistakes
  • Broad credentials + web/tool access = a ready-made exfiltration path.
  • Executing model-generated code unsandboxed.
  • Trusting RAG-retrieved content as if it were your own instructions.

6.5

Serving & Deployment

Applied · the "it runs on my machine" gap
FastAPIasyncAPI-key authSSE streamingDockernon-roottimeoutsjob queue
↩ builds on 1.2 + 1.6
Mental modelAn agent in production is an async, authenticated, containerised service — rate-limited, timed-out, observable.

Wrap the agent in an async API (FastAPI), handle concurrency (1.2), respect upstream rate limits with retries (1.5), enforce timeouts on agent runs, and push long jobs onto a queue so requests don't hang.

Three things that separate a demo from a service, and all three are cheap:

  • Auth. An unauthenticated agent endpoint is a bill anyone on the internet can run up on your behalf — the LLM equivalent of an open mail relay. One header check fixes it.
  • Streaming. An agent takes seconds, so your p95 latency is your user experience. SSE is a plain HTTP response that stays open with data: lines — no WebSocket machinery for one-way output.
  • A container. "It runs on my machine" is not a deployment. A Dockerfile is 20 lines and makes the thing reproducible — and it's the step self-taught builders skip most often.
DrillRun step6_service.py, then call it without the x-api-key header and read the 401. Then docker build -t dorm-agent . and hit the containerised version. Then curl /ask/stream with -N and watch deltas arrive.
Common mistakes
  • Blocking the event loop with a sync call inside an async handler (1.2). This is why the Step 3 loop is async.
  • No timeout on an agent run → a stuck run ties up a worker forever.
  • No auth, because "it's just a demo." Demos get deployed.
  • Trying to return a 500 from a failure that happens mid-stream — the headers are already sent. Errors must be delivered inside the stream.
  • Shipping --reload in a container. It watches the filesystem and there's nothing to reload from.
  • Running the container as root. An agent executes model-chosen actions, so this is worse here than for a plain web app.
  • Holding an HTTP request open for a multi-minute agent run instead of returning a job id.
  • No backpressure — traffic spikes melt your rate limits.

Wire the eval set from 5.4 into CI as a gate that blocks regressions, track pass-rate over time, A/B test prompt and model changes, and monitor production traces (6.1) for drift. This closes the loop: observe → eval → improve.

  • An eval set that never grows as new failures appear in prod.

6.7

Governance & Auditability · new · your differentiator

Backbone ★★★ · the module almost nobody learns
PII redactionaudit trailhash chainapproval gatesretention policydata residencyleast privilege
Mental modelSecurity asks "can an attacker break this?" Governance asks "can you prove what it did?" You need both, and the second one is what gets a system approved for deployment.

Anyone can build an agent. Far fewer can build one that passes a data-protection review. If you work anywhere near regulated data — government, healthcare, finance, education — this is the module that makes you hard to replace, and it is the one almost every self-taught agent builder skips entirely. The good news: it is not AI knowledge. It is ordinary backend discipline — input validation, least privilege, audit trails, retention — applied to a new kind of call. Instincts you already have transfer directly.

Four mechanisms, in the order a request meets them:

  • 1 · Redact. Strip personal data before the model call and substitute placeholders. The cheapest way to answer "what personal data leaves our boundary?" is to be able to say none. The mapping stays in your process and is never written down.
  • 2 · Audit. An append-only record of who asked what, which tools ran, what it cost, and what was decided. Make it hash-chained — each entry carries the hash of the one before — and edits or deletions become detectable. That is the difference between "we have logs" and "our logs are evidence."
  • 3 · Approve. Split tools by blast radius. Read tools run freely; write tools return a proposal and stop, pending a human. This single distinction eliminates the whole category of "the agent did something irreversible while nobody was watching."
  • 4 · Retain. Write down what you keep, for how long, and what you never store — then make the code match the document. Store hashes of prompts and answers rather than the text, and the log can be kept for years without becoming a liability.

Then there's residency: "which country did this inference run in?" should be answerable from configuration (see 2.8), not from faith. That question ends procurement conversations, so being ready for it is leverage.

DrillRun uv run step6b_governance.py --offline — no API key, no cost. It redacts a request, chains four audit entries, proposes a write, approves it, blocks the replay, and verifies the chain. Then open audit-log.jsonl, change one character, and re-run. It will name the exact line that was tampered with. That's about twenty lines of code buying you a property auditors care about a great deal.
Common mistakes
  • A redactor you haven't tested. One that silently misses cases is worse than none, because it manufactures false confidence. Regexes don't catch names, addresses, or free-text disclosure.
  • Logging the full prompt "for debugging" — that's the PII you just carefully redacted, now permanently in your log store.
  • An audit log that's just application logs. If it's mutable and unordered, it isn't an audit trail.
  • Hashing unordered JSON. Without sort_keys the chain can't be recomputed, and a chain you can't verify proves nothing.
  • An approval gate that records the approval separately from performing the write — leaving an "approved but never applied" state nobody notices.
  • Reusable approval tokens. Single-use, or a replayed approval becomes a second write.
  • Writing a policy document the code doesn't implement. That's worse than no policy: you've documented a promise you're breaking.

The capstone — proof you've cleared Step 6

Ship the Step 5 system as a real service

Deploy your multi-agent system so that it is:
  • behind an async FastAPI endpoint              (6.5)
  • authenticated — no anonymous calls            (6.4, 6.5)
  • streaming, so the user isn't watching a
    spinner for eight seconds                     (6.5)
  • traced per request, with tokens AND dollars   (6.1)
  • using prompt caching + right-sized models     (6.2)
  • guarded on input AND output, least-privilege
    tools, injection-aware                        (6.3, 6.4)
  • redacting PII, writing a tamper-evident audit
    trail, gating writes on human approval        (6.7)
  • running in a container, as a non-root user    (6.5)
  • gated by a CI eval that blocks regressions    (6.6)

That's an end-to-end, observable, safe, auditable, evaluated agent service — not a notebook demo. This is the portfolio piece that reads as "employable."

Every bullet above has running code in samples/. That matters: an earlier version of this page promised five things the sample delivered two of. If you extend this capstone, extend the code with it — a spec your own repo doesn't meet is the most quietly corrosive thing in a learning project.

You've finished the track — now get hired

★ From here: build in public

Skills get you interviews only when they're visible. Turn this track into four shippable, talk-about-able projects:

  1. A grounded Q&A bot over a corpus you care about — retrieval, chunking, citations. Ship it with a measured recall number (3.3b); that single table is what makes it interesting rather than another chatbot.
  2. A document extractor that turns a real pile of PDFs or scans into structured records, with a confidence threshold routing the uncertain ones to review (2.9). This is the one most likely to be immediately useful at your job — and the least common in a portfolio.
  3. A tool-calling agent that hits a real API and completes a real task end-to-end (Steps 3–4).
  4. A deployed, auditable agent service — authenticated, traced with per-question cost, eval-gated in CI, PII-redacted, with a tamper-evident audit trail (Steps 5–6, 6.7). The flagship.

Write up each one honestly: what it does, why you built it that way, what broke, and what you'd do next. The "what broke" section is the part experienced engineers actually read.

Two signals worth more than a fourth framework: a number — a pass rate, a recall@k, a cost per question — because it proves you measure instead of guess; and governance (6.7), because "I can build an agent" is common and "I can build one that survives a data-protection review" is rare. On MCP, be precise rather than deep: knowing how to consume servers and being able to explain when a protocol boundary is worth its overhead is the whole signal. You don't need to have authored one.
