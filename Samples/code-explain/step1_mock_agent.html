step1_mock_agent.py

The shape of agent code, with no LLM involved. No API key, no network call — a stand-in "endpoint" plays the model's part so you can learn the plumbing before it costs anything.

What happens when you run it It prints the tool registry, prints one tool's JSON schema, then fires four "tool calls" at the same time and prints four result lines — three successes and one deliberate validation error.

The one idea it teaches An agent is a loop that validates arguments, calls functions concurrently, and turns failures into text instead of crashes — every module in this file exists to serve that one shape.

What it deliberately leaves out There is no language model. mock_call sleeps, randomly fails, and echoes your own payload back wrapped in prose — real reasoning starts in Step 2.

the shape of dispatch() — every exit becomes a string

Both failure paths — bad arguments and a tool call that fails outright — converge on the same shape: a returned string, never an unhandled exception.

1Tool argument models

step1_mock_agent.py:29-36

Two Pydantic classes describing exactly what each tool is allowed to receive.

class WeatherArgs(BaseModel):
    city: str = Field(description="City name")
    units: Literal["c", "f"] = "c"
ConceptThe tool schema as a contract. Literal["c", "f"] means exactly two values are legal — nothing else, ever.
Why this wayThe naive alternative is checking inside the function itself — if units not in ("c","f"): raise. That drifts out of sync as the function grows, and it only exists at runtime. A Pydantic model can also generate its own JSON Schema (used on line 54) — exactly the format an LLM needs to be told what a tool accepts. One declaration becomes both the runtime guard and the documentation you hand the model, instead of two things that can quietly disagree.

2The registry & @tool decorator

step1_mock_agent.py:40-56

TOOLS is a plain dict; @tool(WeatherArgs) registers a function into it under its own name.

ConceptA decorator as registration. TOOLS[fn.__name__] = Tool(...) — the function's name is the tool name, so the two can never fall out of sync.
Why this wayThe naive version is a hand-maintained dict at the bottom of the file. Add a fifth tool, forget the entry, and the agent reports "unknown tool" for a function that plainly exists. Here, defining a tool and registering it are the same act. Notice the decorator returns fn unchanged on line 55 — it adds a side effect and gets out of the way, so get_weather is still an ordinary function you can call and test directly.

3Retry with backoff

step1_mock_agent.py:60-76

Retries a call up to 4 times — but only for one specific, named failure type.

delay = base * (2 ** i) + random.random() * base  # backoff + jitter
ConceptExponential backoff with jitter. Waits roughly grow 0.05s → 0.10s → 0.20s, each nudged by a small random amount.
Why this wayThree decisions hide in these lines. A custom RetryableError class means only transient failures get retried — except Exception would retry your typos too, four times slower to fail. Doubling the delay gives an overloaded service room to recover instead of ten clients hammering it at a fixed rate. Jitter stops those ten clients from retrying together again a moment later — the same thundering herd, just delayed. One more detail: the sleep happens outside the semaphore block on line 94, so a call waiting to retry has already given up its concurrency slot instead of blocking the queue while idle.

4The lazy semaphore

step1_mock_agent.py:81-89

Reads MAX_CONCURRENCY from the environment, but builds the semaphore on first use — not at import.

ConceptConfig from the environment (1.6), plus a real async gotcha: an asyncio object must be created on a running event loop.
Why this wayA semaphore created at module import time attaches to whatever event loop exists then — usually none, or the wrong one — and fails later with a baffling "attached to a different loop" error. Deferring creation until inside an async def guarantees the loop is already running. This one bites people constantly in real async code. Mechanically, a semaphore is just a counter: three calls get in, a fourth waits at async with until one exits — how you stay under a provider's rate limit.

5The mock endpoint

step1_mock_agent.py:92-99

Sleeps briefly, fails about 30% of the time, and returns your own payload wrapped in chatty prose.

Conceptawait asyncio.sleep, never time.sleep, inside async code.
Why this waytime.sleep blocks the entire event loop — every other concurrent call freezes too, and four "parallel" calls quietly become four sequential ones. asyncio.sleep yields control so the others keep moving. This is the single most common async mistake, and the file is built to make it visible if you get it wrong. The prose wrapper is deliberate too: real models return JSON buried in chat text and code fences, and a parser built against clean output breaks the instant it meets a real one.

6Defensive JSON extraction

step1_mock_agent.py:103-107

Regex-finds the first { through the last } in a blob of text, then parses just that.

ConceptNever trust model output to be well-formed. json.loads() on the whole response throws instantly on "Sure!\n```json\n{...}", because it's prose containing JSON, not JSON.
Why this wayre.DOTALL makes . match newlines, so a multi-line object is captured whole. The pattern is deliberately greedy — the right call for one object wrapped in text — but that's also its limit: two JSON objects in one reply, or a stray } in the surrounding prose, and it grabs too much. Fine for this lesson; something worth hardening in a real system.

7dispatch() — the heart of the file

step1_mock_agent.py:124-131

Validates arguments first, calls the tool second, and turns both a validation failure and a failed tool call into a returned string instead of an exception.

except ValidationError as e:
    return f"ERROR: bad args for {name} -- {e.error_count()} problem(s)"
try:
    return await spec.fn(**valid.model_dump())
except Exception as exc:          # retries exhausted, or any other tool failure
    return f"ERROR: {name} failed -- {exc}"
ConceptErrors as data. This is the exact line you hit on your first run — the units: "x" failure is this concept working as intended, not a bug.
Why this wayWithout the first try/except, a bad units value would reach get_weather, raise, and take the whole batch down with it — asyncio.gather() on line 149 propagates the first exception it sees by default, so the other calls' results are lost too. The second try/except exists for a less obvious reason: mock_call fails about half the time per attempt and retries up to 4 times — roughly 1 run in 8 it exhausts all 4 attempts on a weather call and raises RetryableError after validation already passed. Originally only the validation branch was caught, so that retry-exhaustion case still crashed the whole script — a real, easily-reproducible gap caught during a /refactor pass and hardened here. Now every failure, wherever it comes from, becomes a string. In Step 3 that string gets handed back to the model as its own tool result, so it can read its mistake and correct itself next turn — a crash gives the model nothing to learn from.

Traced end to end

One call, followed all the way through:

  1. Input: ("get_weather", {"city": "Tokyo", "units": "f"})
  2. dispatch() looks up TOOLS["get_weather"] — the registered function plus its WeatherArgs contract.
  3. model_validate() checks city is a string and units is "c" or "f". "f" passes.
  4. model_dump() turns that back into {"city": "Tokyo", "units": "f"}, splatted into get_weather(city="Tokyo", units="f").
  5. get_weather builds a payload with a random temperature and awaits mock_call.
  6. The semaphore admits it (or the call waits its turn), it sleeps briefly, and a coin flip decides pass/fail. Say attempt 0 raises RetryableError — the slot is released, the wrapper sleeps ∼0.06s, attempt 1 succeeds.
  7. The reply arrives as prose wrapping JSON; extract_json() strips it down to a real dict.
  8. Output: "27°F in Tokyo", landing in its slot in the results list — in submission order, not finish order.

Traps

  • The ERROR: bad args line is the demo, not a bug. Line 144 sends units: "x" on purpose, with a comment saying so.
  • add prints 42.0, not 42. AddArgs declares a: float, so Pydantic coerces 21 → 21.0. That's type coercion working as intended, not a glitch.
  • Every run looks slightly different. Random temperatures, random sleep durations, random 503s. Different output between runs is normal; only a traceback is a problem.
  • A rare genuine failure is possible. Four consecutive coin-flip failures is about 0.3⁴ ≈ 0.8%. If a RetryableError ever escapes uncaught, that's the retry budget legitimately exhausted — just re-run.
  • MAX_CONCURRENCY is read at import time (line 81), so set it before launching: $env:MAX_CONCURRENCY = "1".
  • No API key needed here. This is the only step that runs fully offline — it just needs pydantic (uv add pydantic), run from inside samples/.

What to watch when you run it

From inside samples/:

uv run step1_mock_agent.py

Three things matter: the printed schema (compare it to WeatherArgs — nothing was written twice), the four result lines (do the three good ones survive the bad one?), and the total runtime (well under a second, even with sleeps and retries — concurrency doing its job).

Predict before you press enter Results print in plan order — Singapore, Tokyo, the sum, then the Oslo error — but the calls actually finish in random order, since they run concurrently. So: is asyncio.gather() sorting the results for you, or is something else going on? Commit to an answer, then set $env:MAX_CONCURRENCY = "1" and run again — if your reasoning was right, you'll know exactly what changes and what doesn't.
