step2_first_call.py

Your first real LLM call. No mock, no key-less shortcut — this is where Step 1's imaginary agent shape meets the real Claude API.

What happens when you run it It prints an input token count, then a structured sentiment classification as a Python dict, then streams a one-sentence answer to a hardcoded question, character by character.

The one idea it teaches A Pydantic model can force an LLM's reply into a shape you validate — the same contract trick from Step 1's tool schemas, now aimed at the model's output instead of a tool's input.

What it deliberately leaves out No retry/backoff (Step 1 had it, this doesn't), no conversation memory between the three calls, no real tool execution — that's Step 3. Every run costs real API tokens.

three lanes, one client, no shared state

Each row is a complete, independent request — none of them sees what the others sent.

Why this wayThe naive move is pasting the key as a string in the script. That key would end up in git history the moment you commit. Reading it from the environment means the same code runs for you, a teammate, or CI, each with their own key, and nothing secret ever touches the file.

2The Sentiment model

step2_first_call.py:27-30

A Pydantic model describing exactly what a sentiment judgment should look like: a label, a confidence score, a reason.

label: Literal["positive", "negative", "neutral"]
confidence: float = Field(ge=0, le=1)
ConceptThe same BaseModel tool from Step 1 (WeatherArgs), but pointed the other direction — describing the model's output, not a function's input.
Why this wayThe naive alternative is Step 1's extract_json trick: ask for JSON in plain prose, then regex it out. That breaks the moment the model adds a caveat sentence or writes "confidence": "high" instead of a number. Forcing the reply through a schema constrains what the model can emit before it even answers; Field(ge=0, le=1) then catches anything that slips through numerically wrong.

3classify() — structured output

step2_first_call.py:33-48

Defines a "tool" the model never actually runs — its only job is to force the reply into Sentiment's shape — then validates what comes back.

tool_choice={"type": "tool", "name": "record_sentiment"}  # force the tool
output_config={"effort": EFFORT}                          # NOT temperature -- see below
Concepttool_choice forcing + effort. Effort controls how much the model reasons before answering: low through max. It is the dial that replaced temperature.
This line used to read temperature=0, and that was a bug. Current models — Sonnet 5, Opus 5, Opus 4.7/4.8 — return a 400 error if temperature, top_p or top_k is set to a non-default value. So the old version of this file, and this walkthrough describing it, could not actually run. It's a useful thing to have happen to you once: the reasoning ("low temperature is right for extraction") was perfectly sound and completely obsolete, and nothing about reading the code would have told you. Only running it does. Module 2.4 covers the three patterns this affects.
Why this wayResponse content is a list of blocks — a model could in principle talk and call a tool in the same reply — so line 47 searches for the tool_use block rather than grabbing msg.content[0] blindly. And even though the tool schema constrains the shape, Sentiment.model_validate(block.input) still re-checks the values on the way back — the same "never trust, always validate" rule as Step 1's dispatch(), now applied to a real model instead of a mock.

4stream_reply() — streaming

step2_first_call.py:52-60

Opens a streaming request and prints each chunk of text the instant it arrives, instead of waiting for the full reply.

ConceptToken-by-token streaming, for perceived latency.
Why this wayThe naive alternative — client.messages.create() then print the whole result — means the terminal (or a chat UI) shows nothing for however many seconds the full answer takes to generate. Streaming lets you show output as it's produced.
This function is now genuinely async, and it wasn't before. It uses get_client(async_=True) with async with / async for. The earlier version used the synchronous client while its comment claimed a tie to module 1.2 (async) — so the track's self-declared keystone skill vanished the moment a real model appeared, and reappeared only as a comment. If it isn't async for, you're still blocking a whole worker for the entire response, which matters enormously by Step 6. It also now calls await stream.get_final_message() at the end, because usage and stop_reason only exist on the completed message.

5count() — tokens before you spend

step2_first_call.py:64-69

Calls a dedicated endpoint that counts how many tokens a prompt will cost before you send it for a completion.

ConceptTokens are the billing and context-window unit — not characters, not words. Counting first is a cost/budget check, not a nice-to-have.
Why this wayEyeballing prompt length in characters is unreliable — tokenization doesn't map 1:1 to characters and varies by content. The comment on lines 77-80 says the real reason this matters: an agent loop re-sends its whole history every turn, so token count — and cost — compounds fast as a conversation grows. That pain shows up for real once Step 3 adds a loop.

Traced end to end

One input, followed through classify():

  1. Input: "The delivery was two days late, but support fixed it in minutes." — deliberately mixed, so the label isn't obvious.
  2. classify() builds a one-tool list from Sentiment.model_json_schema() and wraps the text in "Classify the sentiment of: ...".
  3. client.messages.create() sends it with tool_choice forcing record_sentiment — the model has no option to just reply in prose.
  4. The response's content list is searched for the block where type == "tool_use".
  5. That block's .input — something like {"label": "neutral", "confidence": 0.6, "reason": "..."} — is re-validated through Sentiment.model_validate().
  6. Output: a real Sentiment object, printed as a dict in main().

Traps

  • The token count and the actual request don't match. count(review) counts the raw review text — not the "Classify the sentiment of: ..." wrapper, and not the tool schema, both of which classify() also sends and pays for. The printed number is a lower bound, not the true cost of that call.
  • Non-determinism is expected, and you cannot switch it off. There is no temperature knob any more, so both functions will vary between runs — classify() less, because a forced schema constrains what it can emit, but still not identically. Different wording is normal, not a bug. If you need stability, get it from structure (a schema) and from evals (assert on facts, never on an exact string) — never from a sampling parameter.
  • This needs a real key and spends real money. Unlike Step 1, there's no offline fallback. ANTHROPIC_API_KEY must be set, and the guard on lines 73-74 fails fast with a clear message if it isn't — rather than a cryptic auth error several stack frames down inside the SDK.
  • Three calls, zero shared memory. count(), classify(), and stream_reply() are each an independent, stateless request — none of them sees what the others sent. Step 3 is what adds a running conversation.

What to watch when you run it

From inside samples/, with your key set:

uv run step2_first_call.py

Three lines matter: the input token count, the structured result: {...} dict, and the streamed sentence appearing gradually rather than all at once.

Predict before you press enter The review is deliberately mixed — a late delivery, but support fixed it fast. Before running, commit to a guess: will label come back "positive", "negative", or "neutral"? There's no clean right answer — that's exactly why it's a useful case to watch a real model actually decide.
