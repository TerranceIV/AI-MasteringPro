step2b_document_extract.py

A PDF goes in, a validated Python object comes out. No OCR pipeline, no layout parser, no separate "document AI" service — just Step 2's structured output with a file glued to the front of the message.

What happens when you run it With no arguments it writes sample_inspection.pdf into the folder, sends it to the model, and prints six extracted fields — block, inspector, date, headcount, a list of issues, pass/fail — followed by a confidence verdict.

The one idea it teaches A document is a content block, not a special API. If you can do classify() from Step 2, you can already do document extraction; the only new thing is what you put in the content list.

What it deliberately leaves out Everything that makes this hard at scale: no batching, no Files API upload (it base64s the whole document on every call), no page-range handling for long documents, and no human-review queue — just a printed warning where one would go.

2InspectionRecord — the shape you want back

step2b_document_extract.py:43-55

A Pydantic model describing the six fields to pull out of the form, each with a description.

residents: int = Field(description="Total resident headcount stated on the form")
confidence: float = Field(ge=0, le=1, description="0..1 -- ... Use a LOW value if the
                          document is unclear, partially illegible, or missing fields.")
ConceptThe same model-as-contract idea from module 1.3, pointed at a document. The class defines the schema going out and validates the data coming back.
Why this wayEvery description string here is sent to the model — they are instructions, not code comments. That's why the confidence description spells out when to go low ("unclear, partially illegible, missing fields") instead of just saying "confidence". A bare field name gets you a number the model picked to look reasonable; a described field gets you a number that means something.
Why residents: int matters more than it looksTyping it as int means the model cannot return "four hundred and eighty" or "480 (approx)" and have it slip into your database as a string. The type is doing validation work that you would otherwise write by hand and forget in one place.

3extract() — the whole feature, in one call

step2b_document_extract.py:57-98

Base64-encodes the file, wraps it in a content block, and asks messages.parse() for an InspectionRecord.

block_type = "document" if media_type == "application/pdf" else "image"
file_block = {"type": block_type,
              "source": {"type": "base64", "media_type": media_type, "data": data}}
ConceptMultimodal input as a content block. PDFs use document; images use image. Otherwise they behave identically.
Why the file comes first in the listLook at the order in the content list: file block, then the text instruction. Models follow an instruction more reliably once they have already seen the data it refers to. Put the instruction first and you are asking it to remember a rule while it reads three pages — it works less well, and it is a free fix.
Why messages.parse() instead of a forced toolstep2_first_call.py did this the long way: define a tool, force tool_choice, dig the tool_use block out of the response, then model_validate it. parse() collapses all four steps — you hand it output_format=InspectionRecord and .parsed_output is already an instance. The reason Step 2 did it by hand first is the same reason Step 3 comes before Step 4: you should know what the convenience method is doing before you use it.
The prompt is doing real work"Use exactly what the document says — do not infer or invent values. If a field is genuinely absent, say so in issues and lower your confidence." Without that last sentence the model has no sanctioned way to express "this form is missing the date", so it will quietly produce a plausible one. Give the model a legitimate way to fail and it will usually take it.

5The confidence gate — the actual lesson

step2b_document_extract.py:180-187

Prints a warning if confidence < 0.8 instead of treating the record as final.

if record.confidence < 0.8:
    print("[!] low confidence -- route this document to a human reviewer")
ConceptGuardrails as a routing decision (module 6.3), not as a validation step.
Why this one branch is the whole point of the fileThe model is always willing to give you an answer, and a schema-valid answer looks exactly as confident as a correct one. Schema-valid and factually right are different properties, and nothing in the type system distinguishes them. So you decide the threshold, and low confidence routes to a person rather than to a database. That single if is the difference between a demo and a system an organisation is allowed to depend on — and it's the part that gets left out of every tutorial.
Where the number comes fromNot from intuition: you pick it by labelling a few dozen real documents, seeing what confidence the model assigns to the ones it got wrong, and setting the bar above that. Which is module 3.3b's argument in a different costume — a threshold you haven't measured is a threshold you're guessing at.

Traced end to end

Input: the generated sample_inspection.pdf, a form that says Dorm A, 480 residents, three findings, and "FAILED".

  1. No CLI argument given, so sample_inspection.pdf doesn't exist yet — make_sample_pdf() writes about 1 KB of PDF bytes.
  2. extract() reads those bytes and base64-encodes them into one long ASCII string.
  3. Extension .pdf → media_type="application/pdf" → block_type="document".
  4. One request goes out with a two-item content list: the document block, then the instruction.
  5. The model reads the page and emits an object matching InspectionRecord's schema — it cannot emit anything else, because output_format constrains it.
  6. .parsed_output is already validated: residents arrives as the integer 480, not the string "480".
  7. issues comes back as three list items, one per numbered finding. passed is False — the form says FAILED, and the field description said to use what the document states.
  8. Fields print. confidence is high (the generated form is clean and complete), so the [ok] branch runs.

Traps

  • The generated PDF is deliberately easy. Clean text, no rotation, no handwriting, every field present. Do not conclude from one green run that extraction is solved — test a real scan before you believe anything.
  • confidence is the model's self-report, not a calibrated probability. It's genuinely useful as a relative signal and it is not a statistical guarantee. Treat it as a triage hint.
  • Output varies between runs. Wording inside issues will shift; the numbers shouldn't. Different phrasing is not a bug.
  • A document is untrusted input. Text inside a PDF can carry a prompt injection, and it walks straight past any guardrail that only inspects the user's message. This sample has no defence against that at all — see module 6.4.
  • Base64 inflates by about a third and it's re-sent on every call. Fine for one page; use the Files API once you're uploading the same document repeatedly.
  • Needs ANTHROPIC_API_KEY and anthropic + pydantic. Regenerating the PDF requires nothing.
  • sample_inspection.pdf is gitignored — it's generated, so deleting it is safe.

What to watch when you run it

uv run --with "anthropic,pydantic" step2b_document_extract.py

Three things matter: that residents is an int, that issues has three entries, and the final confidence verdict.

Predict before you run The form says "Overall result: FAILED". Will passed come back False? Now the harder one: the form never mentions a rent amount, and InspectionRecord has no rent field — but issues is a free-text list. Will the model invent an issue to fill it, or leave it at three? Guess, then look.
Then break it on purpose Open make_sample_pdf() and delete the "Date of inspection: 2026-08-14" line, delete the generated PDF, and re-run. inspected_on is a required str, so the model cannot omit it — watch what it does instead, and watch confidence. This is the single most instructive thing you can do with this file: it shows you exactly how a document-extraction pipeline fails in production, which is never with an exception.
