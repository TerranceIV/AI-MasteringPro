The flagship: a real tool-calling agent. Step 2's single call, wrapped in a loop, handed two real tools, a tiny retrieval store, and a growing memory.

What happens when you run it You pass a question on the command line; it prints each tool call live as the model makes it, then prints a final answer once the model stops asking for tools.

The one idea it teaches The entire agent loop — call → check if a tool was requested → run it → feed the result back → repeat — is barely 25 lines. Everything in Steps 1–2 was groundwork for this one loop.

ConceptTwo parallel structures describing the same tools — built by hand this time, instead of derived from one Pydantic model like Step 1's @tool decorator.
Why this wayWorth noticing as a step backward, not forward: Step 1 generated the schema straight from WeatherArgs.model_json_schema(), so the contract and the description could never disagree. Here, TOOLS and TOOL_SCHEMAS are two dicts you keep in sync by hand — add a tool to one and forget the other, and the model either doesn't know a tool exists, or a call reaches dispatch and hits a KeyError. 3The agent loop

step3_agent.py:75-102

Sends the growing message list, checks whether the model wants a tool or is done, and either returns the final text or dispatches every requested tool call.

async def run(task: str, on_usage=None) -> str:
    messages = [{"role": "user", "content": task}]    # 3.4 short-term memory
    for _ in range(MAX_STEPS):                        # 3.6 bounded
        msg = await client.messages.create(...)       # 1.2 async, for real
Concept: memory as a growing list. messages is never cleared — every turn appends to it, and the whole list is resent on every call.
This loop is now async, and that change propagates all the way to Step 6. An earlier version used the synchronous client, which meant Step 5 had to wrap workers in asyncio.to_thread to get concurrency and Step 6 did the same to avoid freezing its event loop — two workarounds for one design decision. Async here and both disappear: Step 5's fan-out is a plain gather, and Step 6 can just await the agent. This is the file where Step 1's insistence on async stops being theoretical.

Also new: on_usage, a callback invoked with the usage object of every model call. That single parameter is the seam Step 6 turns into per-request cost tracing — and running it is how you discover that one user question is several billable calls.
Concept: MAX_STEPS as a guardrail. A hard cap on loop iterations.
Concept: stop_reason as the branch point. If the model didn't ask for a tool, it's done; extract the text and return.
Why this wayThe growing messages list is exactly what Step 2's cost-intuition comment warned about — a conversation's cost compounds because history keeps growing every turn, tokens and all. And without MAX_STEPS, a model stuck calling tools in a loop (e.g. re-searching the same thing because it's never satisfied) would run forever, burning tokens with no ceiling. Six iterations guarantees the function returns — worst case with an honest "stopped: hit MAX_STEPS" message — instead of hanging.

4Tool dispatch + error feedback

step3_agent.py:86-100

Runs each tool the model requested this turn, catching any exception and turning it into a string, then appends every result back into messages.

try:
    output = await TOOLS[block.name](**block.input)   # 3.2 dispatch
    is_error = False
except Exception as exc:                              # 3.6 feed the error BACK
    output, is_error = f"ERROR: {exc}", True

# every result from one turn goes back in ONE user message:
blocks = [b for b in msg.content if b.type == "tool_use"]
tool_results = await asyncio.gather(*(_run_one_tool(b) for b in blocks))
ConceptStep 1's dispatch() pattern again — errors as data, not crashes — but cruder this time.
Two changes here worth understanding, because both are silent failures otherwise.

1. Tools now run concurrently. The model can request several tools in one turn, and gather runs them at once — two 200ms tools take 200ms, not 400ms. But note carefully that every result still goes back in a single user message. Splitting them across separate messages is accepted by the API and quietly teaches the model to stop making parallel calls at all: no error, just an agent that gets slower and pricier over long conversations for no visible reason.

2. is_error=True. Without it, your error string arrives as ordinary data and the model may reason about — or cheerfully report — "ERROR: division by zero" as though it were a result. The flag is what tells it the call failed so it can try something else.
Why this wayNotice what's missing compared to Step 1: no Pydantic validation of block.input before the call. A bare except Exception catches whatever Python happens to raise and turns it into a string the model sees next turn — it works, but you're trusting a raw Python exception message to be a useful correction, instead of a clean, structured "here's exactly what's wrong" from a typed contract. The core lesson still holds: the tool result — success or error — goes back into messages as the next user turn, which is how the model gets to "observe" what it did and react to it.

Traced end to end

Input: "How many residents live across Dorm A and Dorm B combined? Use the tools."

  1. messages starts as one user turn holding the task.
  2. Loop 1: the model decides it needs facts and returns a tool_use block calling search(query="Dorm A Dorm B residents").
  3. TOOLS["search"] keyword-matches DOCS, returning both dorms' resident counts as one string.
  4. That string is appended back into messages as a tool_result.
  5. Loop 2: with both numbers in hand, the model calls calculator(expression="480 + 320").
  6. The regex passes, eval() returns 800, fed back as another tool_result.
  7. Loop 3: the model now has everything it needs and returns plain text — stop_reason != "tool_use".
  8. Output: a final sentence stating 800 residents (exact wording varies between runs).

Traps

  • No key-less mode. Needs ANTHROPIC_API_KEY, checked with the same fail-fast guard as Step 2 (lines 106-107).
  • Non-determinism compounds here. Each of the (up to 6) loop iterations is its own model call — the number of tool calls, their order, and the wording can all vary between runs on the same question. Expected, not a bug.
  • eval() is real risk if ever reused. Fine in this closed demo where only you type the input; never acceptable if calculator received user-facing input in a real service.
  • Silent mismatch risk in TOOLS / TOOL_SCHEMAS. Nothing enforces these two structures agree — unlike Step 1, a mismatch here won't be caught at import time.
  • Hitting MAX_STEPS is a real possible outcome, not just a theoretical guard — a genuinely ambiguous question may legitimately end in "stopped: hit MAX_STEPS...".

What to watch when you run it

From inside samples/, with your key set:

uv run step3_agent.py "How many residents live across Dorm A and Dorm B?"

Watch the [tool] ... lines print live — that's the model's reasoning steps happening in real time, not a final answer appearing out of nowhere. Count how many tool calls it takes.

Predict before you run it Will the model call search once with a combined query, or twice — once per dorm? Both are reasonable; nothing tells it to be efficient, only correct. Guess, then check the printed [tool] lines.
