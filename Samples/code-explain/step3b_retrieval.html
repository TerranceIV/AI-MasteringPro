step3b_retrieval.py

Three retrievers, twelve labelled queries, one table. This file doesn't build an agent — it measures the part of an agent that most often causes what people call hallucination.

What happens when you run it It prints a row per query showing whether each of three retrievers found the right document, then two mean scores, then a short essay about what the numbers mean. Only the third retriever calls the model, so it's cheap.

The one idea it teaches Grade the retriever separately from the agent. Otherwise you cannot tell "the model lied" apart from "the model never saw it" — and those have completely different fixes.

What it deliberately leaves out Real embeddings and a vector index. That absence is the point: two of the twelve queries are unfixable without them, and the file shows you exactly which two rather than asserting that you need a vector database.

two-stage retrieval, and where each stage fails

Stage 1 decides what's possible. Stage 2 only reorders what stage 1 already found.

1DOCS — a corpus with deliberate traps

Eighteen one-line documents about a dormitory.

ConceptNear-duplicates. laundry / laundry-cost, rent / deposit, quiet / noise are pairs that both look plausible for the same query.
Why this wayA toy corpus of five unrelated facts makes every retriever look perfect, which teaches you nothing. Real corpora are full of documents that almost answer the question — and that is precisely what breaks naive retrieval, because the right document is in the pile but not at the top. The near-duplicates here are the whole reason the numbers differ between retrievers.

ConceptA labelled retrieval set. Query → ground truth, written by a human.
Why this is the most valuable block in the fileEverything else here is arithmetic you could copy from anywhere. This list is the thing almost nobody writes, and without it the other 200 lines are meaningless. Ten or twelve labelled queries is enough to turn "our retrieval feels bad" into three distinct, named problems with three different fixes. It took maybe twenty minutes to write.
Why the set is balanced on purposeFour easy queries, three where ranking matters, two where BM25 mis-orders the right answer, two that are lexically impossible. If you only include queries your retriever already handles, your score is a comfortable lie. An eval set should contain the failures you expect and a couple you fear.

3retrieve_naive() — the baseline that's secretly bad

step3b_retrieval.py:90-94

Returns any document sharing at least one word with the query, in whatever order the dictionary happens to iterate.

hits = [doc_id for doc_id, text in DOCS.items() if qs & set(tokens(text))]
return hits[:k]          # note: NO ranking at all -- dict order decides
ConceptBoolean matching with no scoring — membership, not relevance.
Why show a retriever you know is badBecause it's what step3_agent.py's search() does, and it's what most people write first. It isn't wrong — it finds the right document plenty of times. Its flaw is that it has no opinion about order, so with k=3 the answer you need is often present but fourth. Its recall@3 is nearly as good as BM25's; its recall@1 is far worse. That gap is the single most useful thing in the output table.

4bm25_score() — thirty lines that beat the naive version

step3b_retrieval.py:108-125

Scores each document against the query using BM25, then sorts.

idf = math.log(1 + (_N - _DF[w] + 0.5) / (_DF[w] + 0.5))
tf  = freq[w] * (K1 + 1) / (freq[w] + K1 * (1 - B + B * length / _AVG_LEN))
score += idf * tf
ConceptLexical ranking. Two ideas carry all the weight: a word appearing in few documents is more informative (that's idf), and a word appearing ten times isn't ten times more relevant (that's the saturation in tf, tuned by K1).
Why this is the retriever to beat before you buy anythingNo embeddings. No index build. No database. No API calls. No dimension to choose, no model to keep in sync between index time and query time. It is pure arithmetic over the documents you already have — and it produces the largest single jump in the output table. If you take one thing from this file: fix your lexical baseline before you shop for infrastructure.
The _DF / _AVG_LEN globalsComputed once at import from the whole corpus, because IDF is a property of the collection, not of a document. In a real system these are the numbers that go stale when documents change — which is the mundane reason "keeping the index fresh" is a real engineering concern rather than a detail.

5retrieve_reranked() — cheap recall, expensive precision

step3b_retrieval.py:136-161

Takes BM25's top six, shows them to the model, and asks for them back in relevance order with the irrelevant ones dropped.

...
output_config={"effort": "low"},            # reranking is a narrow judgement
output_format=Ranking,
ConceptTwo-stage retrieval — a cheap wide net, then an expensive narrow filter. Almost every good retrieval system has this shape.
Why retrieve 6 to return 3Because a reranker can only reorder what it is given. If you hand it exactly the three you were going to return, it has nothing to fix. The wide-then-narrow split is what makes the second stage useful and affordable — the model sees six short documents, not eighteen, and never the whole corpus.
Why effort: "low""Which of these six answers the question?" is a narrow judgement, not a reasoning problem. High effort would cost more and change nothing. This is module 2.4's dial being used properly: match the effort to the difficulty of the decision, and reserve the expensive settings for the calls that earn them.
The Ranking model earns its keepAsking for prose — "put these in order" — gets you a paragraph you then have to parse. output_format=Ranking gets you list[str]. And note the guard on the next line: [d for d in ...doc_ids if d in DOCS], because a model asked for ids can return an id that doesn't exist. Validate on the way back even when the schema constrained the way out.

6recall_at_k() — the metric, in one line

step3b_retrieval.py:164-166

return len(set(got[:k]) & want) / len(want)
Conceptrecall@k — of the documents that should have come back, what fraction appeared in the top k?
Why recall and not precisionFor feeding an agent, missing the right document is fatal and carrying one extra irrelevant one is merely wasteful — the model is good at ignoring a bad chunk and helpless without a good one. So recall is the metric that matters here. Watch both @1 and @3 though: the gap between them is exactly the space a reranker can win back, and comparing the two columns tells you whether your problem is finding or ordering.

Traced end to end

Query: "Where can I leave my bicycle?", expected: {"bicycle"}

  1. tokens() strips stopwords → ["leave", "bicycle"].
  2. naive: both visitors ("...and leave by 10pm") and bicycle ("Bicycle racks...") share a word. Dict order puts visitors first → recall@1 = 0.00, recall@3 = 1.00.
  3. BM25: scores both. "leave" and "bicycle" are each rare, so the scores land close — and visitors still edges ahead → recall@1 = 0.00, recall@3 = 1.00. Better maths, same wrong winner.
  4. rerank: BM25's top 6 (including both) go to the model with the question. It sees that a rule about visitor curfew does not answer "where do I put my bike" and drops it → bicycle first, recall@1 = 1.00.
  5. This is the row that justifies the third retriever's existence: the document was always retrievable, and only ranking was broken.
Now the contrasting row"Can I keep a cat?" → tokens ["keep", "cat"]. Neither word appears in any document (pets says "Pets are not permitted..."). BM25 returns an empty candidate list, so the reranker is handed nothing and returns nothing. All three retrievers score 0.00. No amount of lexical tuning fixes this, and that is the one honest argument for adding embeddings.

Traps

  • Two rows are supposed to be 0.00 everywhere. "Can I keep a cat?" and "Where do I wash clothes?" fail by design — they are the vocabulary-mismatch demonstration, not a broken retriever.
  • The measured averages are modest, and that's deliberate. Roughly naive@1 0.46 → BM25@1 0.71 → rerank ceiling 0.83. A tutorial that makes reranking look heroic has usually rigged the corpus. The shape of these numbers — big free win, moderate paid win, hard ceiling — is the realistic one.
  • Only the rerank column costs money, one small call per query. Naive and BM25 make zero API calls.
  • Rerank output varies slightly between runs. A borderline row may flip. Don't treat a single run as a measurement — that variance is itself a lesson about judge-style evaluation.
  • The corpus is 18 one-line documents. Real chunking decisions — how big, where to split, how much overlap — don't appear here at all.
  • Needs ANTHROPIC_API_KEY, plus anthropic and pydantic.

What to watch when you run it

uv run --with "anthropic,pydantic" step3b_retrieval.py

Don't read the averages first. Read which rows differ between columns — that's where the information is.

Predict before you run Which will be the bigger jump: naive@1 → BM25@1, or BM25@1 → rerank@1? Most people guess the reranker, because it involves the model. Guess, then look — and if you guessed wrong, that misconception was about to cost you a vector database.
Then earn the vector index Add one word to the pets document — say "Cats, dogs and other pets are not permitted..." — and re-run. "Can I keep a cat?" jumps from 0.00 to 1.00 with no model involved. That's the lesson: vocabulary mismatch is sometimes a content problem, not an infrastructure problem. Check which one you have before you buy the infrastructure.
