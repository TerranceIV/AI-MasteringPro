step5_orchestrator.py

Orchestrator/worker fan-out. Splits a question into subtasks, runs them as separate Step-3 agents concurrently, synthesizes their findings, and scores itself against the 12-case eval suite in evals.py.

What happens when you run it Twelve [PASS]/[FAIL] lines with their answers, then a pass rate: x/12 summary.

The one idea it teaches Fan a question out to several independent agent runs in parallel, have a separate model call synthesize their findings into one answer, and score the whole thing automatically instead of eyeballing it.

What it deliberately leaves out The subtask split is hand-written per case, not decided by a model. The "eval" is a crude substring check, not real grading. No retry if a worker fails.

fan-out, then fan-in

Both workers are full Step-3 agents running concurrently — the wall-clock cost is the slower one, not the sum of both.

1Reusing Step 3 as a worker

step5_orchestrator.py:13-22

from step3_agent import run as worker — literally imports Step 3's agent loop and uses it as a black-box worker.

ConceptComposition — an agent calling other agents.
Why this wayThe naive alternative is copy-pasting Step 3's loop into this file. Importing it directly guarantees the worker behaves identically to the standalone Step 3 agent — same tools, same MAX_STEPS, same guardrails — and any future fix to Step 3 improves Step 5 for free.

2run_worker() — bridging sync into async

step5_orchestrator.py:25-28

findings = await asyncio.gather(*(worker(s) for s in subtasks))   # 5.2 fan-out
Conceptasyncio.gather runs every worker concurrently. Three workers taking 3 seconds each finish in about 3 seconds, not 9.
This used to read await asyncio.to_thread(worker, subtask), and the reason is worth keeping in mind. step3_agent.run() was synchronous, so it couldn't be awaited — calling it directly inside an async def would have frozen the event loop for the very workers you were trying to parallelise. to_thread is the correct fix for that situation: it pushes a blocking function onto an OS thread. Keep it in your toolkit for wrapping genuinely synchronous libraries.

But it was treating a symptom. Now that the Step 3 loop is async, the fan-out is a plain gather over coroutines — no threads, no pool to size, no hidden ceiling on concurrency. The general lesson: when you find yourself reaching for to_thread on code you own, the real fix is usually one layer down.

3synthesize()

step5_orchestrator.py:31-44

Takes the question plus a list of plain-string worker findings and makes one more LLM call to combine them into a single answer.

ConceptA synthesis/manager step, distinct from the worker steps — it aggregates, it doesn't retrieve.
Why this wayThe naive alternative is just concatenating the raw findings. Fine for two short facts; doesn't scale to many subtasks or findings that overlap or conflict. A model reconciling several reports into one coherent answer is the same reason a human project lead writes a summary instead of forwarding five raw emails.

4orchestrate() — fan-out/fan-in

step5_orchestrator.py:47-49

findings = await asyncio.gather(*(run_worker(s) for s in subtasks))  # 5.2 fan-out
return synthesize(question, list(findings))                          # 5.2 synthesize
ConceptAll subtasks run concurrently, then one synthesis call combines them.
Why this wayAwaiting workers one at a time would take the sum of every worker's full multi-turn agent loop — potentially the slowest part of the whole system, since each worker can itself take several round-trips. Running them concurrently makes total wall-clock roughly equal to the single slowest worker — the same asyncio.gather idea as Step 1, now fanning out entire sub-agents instead of single tool calls.

5The eval suite — now in evals.py

evals.py  ·  run by step5_orchestrator.py and by CI

Twelve cases, each with hand-written subtasks and either an expected substring or a grading rubric. run_suite() runs them concurrently and reports a pass rate.

ConceptAn eval set — a small, repeatable regression test for agent behavior, not just code correctness.
Why this wayEyeballing the answer after every prompt/tool/model tweak doesn't scale and doesn't catch regressions you weren't looking for. A pass rate gives you one number to watch. It lives in its own module now because the CI workflow imports it too — the same suite you run by hand is the one that blocks a merge, which is the whole point of module 6.6.
This grew from 2 cases to 12, and gained a second grader — both for specific reasons.

Two graders. Eight cases use a free substring check; four use an LLM judge with a rubric. Use the cheapest grader that can do the job: a mostly-deterministic suite runs in seconds and never flakes, which is the only property that makes it get run at all.

Why a judge is sometimes unavoidable. Take "Which block has more residents, Dorm A or Dorm B?" — a check for "Dorm A" in answer also passes on "Dorm B has more residents than Dorm A", the exactly-wrong answer. A substring test can verify a fact; it cannot verify a relation.

The two most valuable cases are refusals. grounding-unknown-block asks about a Dorm Z that isn't in the knowledge base. The correct behaviour is to decline, and no assertion can express "must not invent a number" — you'd have to assert the absence of every fabricated value, phrased any number of ways. An agent's real reliability lives in what it refuses to say, and those cases are the first thing a careful interviewer probes.
Worth noticing, still: the subtask split is written by a human, not decided by a model — a genuinely dynamic orchestrator would have an LLM do that decomposition itself.

Traced end to end

Eval case 2: "What is the total number of residents across Dorm A and Dorm B?"

  1. subtasks = ["How many residents live in Dorm A?", "How many residents live in Dorm B?"].
  2. orchestrate calls asyncio.gather(run_worker(s1), run_worker(s2)) — both start together, each on its own thread running a full Step-3 agent loop.
  3. Worker 1's internal loop calls search(...) for Dorm A and returns its resident count; worker 2 does the same for Dorm B, in parallel.
  4. Both findings return via gather, in submission order regardless of which finished first.
  5. synthesize(question, findings) sends one more message asking for "a single concise final answer" — the model replies with the combined total.
  6. Output: "800" in answer → True → [PASS]. Once all twelve cases finish: pass rate: 12/12 (100%) — on a good day. The refusal cases are the ones most likely to cost you a point.

Traps

  • Two full agent runs per eval case, not two single calls. Each "worker" is itself a multi-turn Step-3 loop — one eval case can trigger several LLM calls total.
  • The eval check is a crude substring match. "Eight hundred residents" instead of "800" would fail even though it's right — not something to trust as real evaluation.
  • Subtasks are hand-written, not model-decided. A human wrote the split for each eval case; the orchestrator itself doesn't decompose questions.
  • Needs ANTHROPIC_API_KEY, and must run from inside samples/ since it imports step3_agent.
  • Inherits Step 3's non-determinism and its eval()-based calculator risk, since every worker is a Step 3 agent.
