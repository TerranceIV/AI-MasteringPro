/explain · step 5b

step5b_mcp_client.py

An agent that gains tools it was never coded against. This client hardcodes no tool schemas at all — it asks a server what it can do, and hands the answer to the model. That's the entire payoff of a protocol.

What happens when you run it It launches mcp_dorm_server.py as a background subprocess, prints the tools that server advertises, then answers a question using them — showing each [mcp] tool call as it happens.

The one idea it teaches Runtime discovery. Nothing below the SERVER constant knows what tools exist. Point it at a different server and the client works unchanged.

What it deliberately leaves out Auth, remote transport, and any trust boundary. It spawns a local script it already trusts. A real client talking to a third-party server has to worry about credentials, and about the fact that tool descriptions from that server land in your prompt.

ConceptTwo separate projects. mcp is the protocol SDK, maintained independently of Anthropic. anthropic.lib.tools.mcp is a small adapter that turns MCP's tool objects into the shape the Messages API wants.
Why that split mattersMCP is an open standard, not an Anthropic feature — the same server works with other clients and other models. The adapter is the only Anthropic-specific line here. Needs anthropic[mcp] and Python 3.10+.

2SERVER — the only line that knows anything

SERVER = StdioServerParameters(
    command=sys.executable,           # the same Python that's running us
    args=["mcp_dorm_server.py"],
)
Conceptstdio transport. The client launches the server as a child process and talks to it over the pipes — the same mechanism a shell uses.
Why sys.executable rather than "python"Under uv run the interpreter with your dependencies installed is not necessarily the python on PATH. sys.executable is whichever interpreter is running this file, so the child gets the same environment. This is the sort of one-line detail that produces a baffling ModuleNotFoundError from a subprocess.
This is the whole configuration surfaceSwap these two values for uvx mcp-server-fetch, or a vendor's server, or your own, and nothing else in the file changes. That is the claim MCP makes, and this constant is where you can check it.

3Discovery — the part worth watching

step5b_mcp_client.py:42-57

Opens the connection, handshakes, asks for the tool list, and prints it.

async with stdio_client(SERVER) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()
        listed = await session.list_tools()      # 5.3 we did NOT hardcode these
ConceptCapability negotiation. initialize() is the handshake; list_tools() is the client asking "what can you do?"
Why the two nested async with blocksThe outer one owns the subprocess — leaving it kills the server. The inner one owns the protocol session. Nesting them means a crash anywhere cleans up both, in order, with no orphaned Python process left running. This is plumbing, but it's the kind whose absence you discover via Task Manager.
Why printing the tool list is the point of the sampleCompare with step3_agent.py's TOOL_SCHEMAS: forty lines of hand-written JSON Schema, which must be kept in sync with the Python functions by hand. Here that list arrives. Add a tool to the server and re-run the client with no edits — it will use the new tool. That gap is the entire argument for a protocol boundary, and it's why the track rates consuming MCP as worth an hour of your life.

async for message in runner:      # the loop you wrote by hand in Step 3
ConceptThe SDK's built-in agent loop. async_mcp_tool bundles the schema and a callable that forwards execution back over the MCP session.
Why it's safe to let the SDK do it hereBecause you already wrote this loop. tool_runner is doing exactly what step3_agent.py does: call the model, check for tool requests, run them, append results, repeat until it stops asking. You can predict its behaviour and debug it when it misbehaves. That's the only reason to use it — and it's why Step 3 comes before Step 4.
What it costs youThe step cap is now the SDK's business, not yours. If a model loops on a tool, you have less direct control than the plain for _ in range(MAX_STEPS) you wrote yourself. Fine for a demo; something to check before production.
The [mcp] print is deliberateIterating the runner is the only window you get into a loop you didn't write. Printing each tool_use block as it passes is a poor man's trace — and a reminder that with a framework, observability stops being free.

5The server side, in one glance

mcp_dorm_server.py:31-52

Two functions with a decorator, and mcp.run().

@mcp.tool()
def search_dorm_facts(query: str) -> str:
    """Search the dormitory knowledge base for facts about blocks and rules.

    Args:
        query: Words to look for, e.g. "Dorm A residents" or "quiet hours".
    """
ConceptSignature and docstring become the schema. The type hints produce the JSON Schema; the docstring becomes the description the model reads.
Why this looks familiarIt's module 1.3's Pydantic-model-as-contract, standardised across an ecosystem. The decorator does what you built by hand in step1_mock_agent.py's register_tool — which is why that Step 1 drill about capturing docstrings via inspect was pointing here all along.
Read this file once, then don't write one for a whileThe track's position: consuming servers is ★★, authoring them is ○ until you have something specific to expose. The API is small and you'll learn it in an afternoon on the day you need it. Your realistic ratio is many servers consumed per one written — and if nothing else will ever consume it, a protocol boundary is pure overhead over a plain function.

Traced end to end

Question: "How many residents are in Dorm A and Dorm B in total?"

  1. stdio_client spawns python mcp_dorm_server.py. The server starts and waits on stdin — it prints nothing you'll see.
  2. initialize() exchanges protocol versions and capabilities.
  3. list_tools() returns two entries. The client prints search_dorm_facts and list_blocks with their descriptions — the first proof that discovery worked.
  4. Each is wrapped by async_mcp_tool into something with a schema and an executor.
  5. The runner sends the question plus both tool definitions. The model asks for search_dorm_facts(query="Dorm A Dorm B residents").
  6. The client prints [mcp] search_dorm_facts({'query': ...}), and the call travels over the pipe to the other process, which keyword-matches its own DOCS and returns both dorm lines.
  7. The result comes back as a tool_result; the runner appends it and re-calls the model.
  8. The model has 480 and 320. Note there is no calculator tool here — it adds them itself and answers 800. Fewer tools than Step 3, so it does the arithmetic in its head.
  9. The loop ends; the final text prints. Leaving the async with blocks shuts the subprocess down.

Traps

  • Must be run from inside samples/. args=["mcp_dorm_server.py"] is a relative path; from elsewhere the subprocess dies and you get a connection error rather than a clear "file not found".
  • Needs the full dependency string: uv run --with "anthropic[mcp],mcp" step5b_mcp_client.py. Plain --with anthropic gives you No module named 'mcp'.
  • Python 3.10+. The MCP SDK requires it.
  • The server prints nothing on success. Silence from it is correct — it's speaking a protocol on stdout, not logging. Anything it printed to stdout would corrupt that stream.
  • Never run mcp_dorm_server.py expecting output. It waits for a client on stdin and looks hung. That's not a bug.
  • The model does its own arithmetic here. With no calculator tool, the total is computed by the model — fine for 480+320, not something to rely on generally.
  • No trust boundary at all. This spawns a local file you wrote. A third-party server sees every argument you send it, and its tool descriptions go into your prompt — a hostile server is an injection vector (module 6.4).
  • Needs ANTHROPIC_API_KEY.

What to watch when you run it

uv run --with "anthropic[mcp],mcp" step5b_mcp_client.py uv run --with "anthropic[mcp],mcp" step5b_mcp_client.py "list every block on record"

Watch the discovered-tools list first, then which tool the model picks. The second command should make it choose list_blocks instead — a choice nothing in the client code influences.

Predict before you run There is no calculator tool. Will the model refuse to total the two numbers, call search_dorm_facts twice, or just add them itself? Guess, then look at the [mcp] lines.
Then prove the protocol claim Add a third tool to mcp_dorm_server.py — say count_residents(block: str) -> int — and re-run the client without editing it. It will appear in the discovered list and the model will use it. Compare that against what adding a tool to step3_agent.py costs you: a function, a registry entry, and a hand-written JSON schema kept in sync. That difference is the whole value proposition, and now you've measured it rather than read about it.
