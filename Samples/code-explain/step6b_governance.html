step6b_governance.py

The file that gets an agent approved, not just working. Security asks whether an attacker can break your system. Governance asks whether you can prove what it did — and in a regulated environment the second question is the one that decides whether you ship.

What happens when you run it Five numbered sections print in order: a request with its personal data stripped out, a model answer, a write proposal that gets approved and then replayed and blocked, a verified audit chain, and the retention policy. With --offline it uses a canned answer — no API key, no cost, no network.

The one idea it teaches None of this is AI knowledge. It's ordinary backend discipline — validate input, least privilege, audit trails, retention — applied to a new kind of call. Which is exactly why it's a differentiator: most people learning agents skip it, and most organisations can't deploy without it.

What it deliberately leaves out The PII regexes are illustrative and will miss things — names, addresses, anything disclosed in free text. Real deployments use a dedicated detection service. There's also no database, no real write, and no access control on who may approve.

1redact() — make the answer "none"

step6b_governance.py:54-78

Replaces NRIC numbers, emails, phone numbers and card-shaped digit runs with stable placeholders, returning the safe text plus the mapping needed to reverse it.

for token, value in mapping.items():   # reuse the same token
    if value == original:              # for a repeat mention
        return token
ConceptTokenised redaction. The model reasons over [NRIC_1] and never needs to resolve it, because it doesn't need the real value to answer the question.
Why redact before the call and not in the logsBecause the auditor's question is "what personal data leaves our boundary?", and the strongest possible answer is none — provably, by construction. Redacting only in your own logs still sent the data to a third party; you've just made your own records harder to search. The best control is the one that makes the data never exist in that path.
Why the same value must map to the same tokenThat inner loop looks like a micro-optimisation and isn't. If the same NRIC appeared twice and became [NRIC_1] and [NRIC_2], the model would think there were two people. Stable tokens preserve the relationships in the text while destroying the identities — which is what makes redacted text still useful to reason over.
The honest warning in the docstring"A redactor that quietly misses things is worse than none, since it manufactures false confidence." Regexes catch structured identifiers. They do not catch "the resident in unit 7-12 whose son attends the primary school nearby" — which identifies someone perfectly well. Take this block as the shape of the control, not an implementation to ship.

2AuditLog — logs vs. evidence

step6b_governance.py:91-157

Appends JSON lines, each carrying the SHA-256 hash of the entry before it, and can recompute the whole chain to prove nothing was altered.

payload = prev + json.dumps(entry, sort_keys=True, separators=(",", ":"))
return hashlib.sha256(payload.encode("utf-8")).hexdigest()
ConceptA hash chain. Each entry commits to its predecessor, so editing or removing any past line breaks every hash after it.
Why a plain log isn't enoughThe question an auditor actually asks is not "do you have logs?" but "could someone have quietly changed them?" An ordinary application log has no answer. This does — and it's about twenty lines. That ratio of effort to credibility is why this block is worth studying even though there's nothing clever in it.
sort_keys=True is load-bearingPython dict ordering would otherwise leak into the hash, and a chain you cannot reproduce proves nothing at all. separators pins the formatting for the same reason. Get this wrong and you have a system that looks tamper-evident and isn't — the worst of both worlds.
What is stored, and what deliberately isn'tLook at the fields: prompt_hash, response_hash, args_hash — never the text. That gives you provable "this exact question produced this exact answer" without retaining the personal data. So the log can be kept for seven years without itself becoming the liability. This is the design decision that makes long retention safe, and it's the one most people get backwards.
verify() returns a line numberNot a boolean. "Your audit trail is intact" and "line 3 was modified after writing" are different products, and the second is the one you can act on.

3The approval gate — splitting tools by blast radius

step6b_governance.py:171-200

Read tools run freely. Write tools return a PENDING APPROVAL string with a single-use token; a separate approve_write() call commits it.

READ_TOOLS  = {"search", "calculator"}
WRITE_TOOLS = {"update_resident_count", "send_notice"}
...
pending = _PENDING.pop(token, None)      # pop, not get -- single use
ConceptLeast privilege for agents, expressed as a distinction the agent cannot cross on its own: it may propose, a human must commit.
Why this one distinction is worth more than any guardrailIt eliminates an entire category of failure — "the agent did something irreversible while nobody was watching" — rather than trying to detect bad instances of it. A blocklist has to anticipate the attack; this doesn't have to. Prompt injection that reaches a read tool is an information problem; the same injection reaching an unguarded write tool is an incident.
.pop() is the security controlUsing .get() would let an approval be replayed into a second write. The demo calls approve_write twice on purpose so you can watch the second attempt get rejected and recorded — note that the rejection also appends an audit entry. A failed attempt is exactly the thing you most want in the log.
The gap this sample admits toThe comment in approve_write says a real system performs the write inside the same transaction that records the approval. Otherwise you can end up "approved but never applied" — a state nobody monitors and everyone assumes away. Also missing here: any check that approver is allowed to approve, and that they aren't the same person who requested it.

5main() and --offline

Runs one request through all four gates, printing each stage.

if offline:

else:

    answer = await agent(safe)
Why the import is inside the functionstep3_agent.py builds a client at import time, which needs an API key. Importing it at the top would make --offline require the very key it exists to avoid. Moving one import inside a branch is what makes the free path actually free.
Why an offline mode at allThe governance mechanics — redaction, chaining, approval, verification — have nothing to do with the model. Making them runnable at zero cost means you can read, break, and re-run this file as many times as you like. The cheapest lesson in the repo is also the most differentiating one.
Note what the model is asked to do, and refusesThe request contains "Please also update the resident count for Dorm A to 481." The agent has no write tool — so it answers the question and the update becomes a proposal for a human. The agent didn't decide to be careful; the tool surface made carelessness impossible. Design the tool surface, not the prompt.

Traced end to end

Input: "Resident S1234567D (tan.wei.ming@example.com, mobile 91234567) asked how many residents live in Dorm A and Dorm B in total. Please also update the resident count for Dorm A to 481."

  1. redact() finds three items → [NRIC_1], [EMAIL_1], [PHONE_1]. The mapping dict holds the originals and is never written anywhere.
  2. Audit entry 1: request_received, with prompt_hash of the redacted text and pii_items: 3. prev_hash is 64 zeros — the genesis entry.
  3. The redacted text goes to the model (or the canned answer under --offline). Note the question still makes sense with placeholders — the identity was never needed to count residents.
  4. Audit entry 2: response_produced, with a hash of the answer. Its prev_hash equals entry 1's entry_hash.
  5. propose_write() mints a token, stashes the pending action, and appends entry 3: write_proposed — recording an args_hash, not the arguments.
  6. approve_write(token, "supervisor:lim") pops the token, appends entry 4: write_approved, and reports success.
  7. The same token again → already popped → entry 5: approval_rejected, reason "unknown or already-used token". Printed as <- replay blocked.
  8. verify() walks all five lines, recomputing each hash from the previous one: 5 entries verified, chain intact.

Traps

  • The second "no pending action" line is the demo working. It's the replay being blocked, printed on purpose. Not an error.
  • audit-log.jsonl appends across runs and is gitignored. Run twice and verify() counts 10 entries — correct, not a leak. Delete the file to start clean.
  • The approval token changes every run (it's a fresh UUID), so it won't match anything you copied from a previous run.
  • The PII regexes are Singapore-shaped and illustrative. The NRIC and mobile patterns won't fit other jurisdictions, and none of them catch names or addresses. Read the docstring's warning before reusing any of it.
  • The CARD pattern is broad — any 13-19 digit run. On documents full of reference numbers it will over-redact. Over-redaction is the safer failure, but it's still a failure.
  • --offline needs no key and makes no network call. Without the flag you need ANTHROPIC_API_KEY and must run from inside samples/.
  • Nothing here is a real write. approve_write logs and returns a string; there is no database.

What to watch when you run it

uv run step6b_governance.py --offline

Three things: that the redacted text still reads sensibly, that the write became a proposal rather than an action, and the verify(): OK line.

Predict before you run The request asks to change a resident count. Will the agent do it, refuse it, or something else? And in the audit log, will you find the resident's email address anywhere — hashed, redacted, or plain? Guess both, then check audit-log.jsonl yourself.
Then break the chain — do this one, it's the whole point Open audit-log.jsonl, change a single character inside any line (an actor name is easiest), save, and re-run with --offline. verify() names the exact line: line 3: entry was modified after writing. Now instead delete a whole line and re-run — you get line 2: chain break (prev_hash mismatch), because deletion breaks the link rather than the content.

That's tamper-evidence: you cannot stop someone editing a file they can write to, but you can guarantee it is detectable. Twenty lines of code, and it's the difference between records and evidence.
