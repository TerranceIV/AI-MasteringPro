Dockerfile

The step most self-taught agent builders skip. "It runs on my machine" is not a deployment — and this is twenty lines that turn the Step 6 service into a reproducible artifact you can hand to someone else.

What happens when you run it docker build produces an image; docker run starts the FastAPI service on port 8000 with a health check, as a non-root user. Same behaviour as running uvicorn locally, minus your laptop.

The one idea it teaches Layer ordering and least privilege. Dependencies go in their own layer because they change rarely; the process drops out of root because an agent executes model-chosen actions.

What it deliberately leaves out A lockfile (it pins minimums, not exact versions), multi-stage builds, and any orchestration — no compose file, no Kubernetes manifest, no secret management beyond -e.

why the order of these lines matters

Docker caches per layer. Everything below a changed layer is rebuilt.

1FROM python:3.12-slim + the uv binary

Dockerfile:14-18

FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
ConceptA multi-source copy. COPY --from pulls files out of another image without making it your base.
Why -slimRoughly a tenth the size of the full image. Smaller means faster pulls, less disk, and a smaller attack surface — fewer packages installed means fewer CVEs to answer for at review time. The cost is no build toolchain and no curl, which the health check works around later.
Why copy uv in rather than pip install uvYou get the same tool you use locally, at a fixed known-good build, without a Python-level install step. It's the pattern Astral document, and the general trick is worth knowing: you can lift a static binary out of any published image without inheriting that image's OS.
The version pin you'd want in productionpython:3.12-slim is a moving tag — it changes as patches land. Reproducible builds pin a digest. Fine for a sample; not fine for something you must rebuild identically in six months.

2ENV — three settings, one that actually matters

Dockerfile:21-23

ENV UV_SYSTEM_PYTHON=1 \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
ConceptContainer-appropriate Python defaults.
PYTHONUNBUFFERED=1 is the one that will bite youPython buffers stdout when it isn't a terminal. In a container that means your logs vanish — they sit in a buffer, and if the process is killed you lose them entirely. For step6_service.py, whose whole observability story is one JSON line per request, that would quietly defeat the point. This is the single most valuable line in the file.
The other twoUV_SYSTEM_PYTHON=1 tells uv to install into the image's Python rather than making a venv — the container is the isolation, so a venv inside it is a layer of indirection for nothing. PYTHONDONTWRITEBYTECODE=1 skips .pyc files, which would just bloat the image. Both are hygiene; neither will ruin your day.

3The dependency layer — the caching lesson

Dockerfile:29-38

Installs four packages, then copies the application code.

RUN uv pip install --system --no-cache \
        "anthropic>=0.40" "fastapi>=0.110" "uvicorn[standard]>=0.30" "pydantic>=2.6"

COPY config.py step3_agent.py step6_service.py ./
ConceptLayer caching. Docker reuses a layer if its inputs are unchanged, and invalidates everything below a layer that changed.
Why dependencies come before code — test this yourselfYour code changes many times an hour; your dependencies change monthly. In this order, editing a .py file rebuilds only the last two layers: about a second. Swap the two lines and every code edit re-downloads and reinstalls four packages — tens of seconds, every time. Same image, same correctness, a build loop you'll come to resent.
Why --no-cacheuv's download cache is useless inside a finished image — it's write-once. Skipping it keeps the layer smaller. (Note it means the opposite of what it sounds like: it disables uv's package cache, not Docker's layer cache, which you very much want.)
Why only three files are copiedNot the whole repo. Two reasons, and the second is the important one: a smaller image, and no accidental secrets baked into a layer forever. Copy the directory wholesale and a stray .env or an audit-log.jsonl is in the image permanently — deleting it in a later layer does not remove it, because layers are additive. Being explicit is the defence.
What production does insteadCopies a uv.lock and installs from it, so the build is byte-reproducible. Minimum-version pins keep this sample from rotting as packages move, at the cost of "works today, maybe differently next month".

4USER appuser — two lines of real security

Dockerfile:43-44

RUN useradd --system --uid 10001 appuser
USER appuser
ConceptLeast privilege (module 6.4). Containers run as root unless you say otherwise.
Why this matters more for an agent than for a plain web appAn agent executes actions the model chose. This sample's calculator tool literally calls eval() behind a regex allowlist. Root inside a container isn't root on the host, but it's a meaningfully worse starting position for any escape or misconfiguration — and you are one careless tool away from finding out. Two lines.
Why after the installsInstalling needs root. Switch earlier and uv pip install --system fails on permissions. Order is forced: privileged setup first, then drop, then run.
Why an explicit high uid--uid 10001 is predictable, which matters when a mounted volume needs matching ownership. --system skips the home directory and password entry a service account has no use for.

5HEALTHCHECK and CMD

Dockerfile:49-54

HEALTHCHECK --interval=30s --timeout=5s --start-period=5s --retries=3 \
    CMD python -c "import urllib.request as u; u.urlopen('http://127.0.0.1:8000/health')"

CMD ["uvicorn", "step6_service:app", "--host", "0.0.0.0", "--port", "8000"]
ConceptLiveness as a container-level contract, so an orchestrator can restart or de-register an unhealthy instance without knowing anything about your app.
Why Python and not curlpython:*-slim has no curl. Rather than install a package purely to make one HTTP request, use the interpreter that's already there. Reach for what's in the image before you add to it.
Why /health and not /ask/health needs no API key and makes no model call. Health-checking a real endpoint every 30 seconds would burn tokens forever and fail whenever the upstream API had a hiccup — conflating "my process is alive" with "my dependency is up", which are different questions with different remedies.
Why --host 0.0.0.0 is requireduvicorn defaults to 127.0.0.1, which inside a container means "reachable only from inside this container". Your -p 8000:8000 would map to nothing and you'd get a connection refused that looks like a Docker problem. This is the classic first-container bug.
Why no --reloadIt watches the filesystem, roughly doubles memory, and there is nothing to reload from — the code is baked into the image. That flag belongs on your laptop only.

Traced end to end

A first build, an edit, and a run.

  1. docker build -t dorm-agent . from inside samples/ — the build context is that folder.
  2. Base image pulled if absent. uv is copied out of Astral's image into /bin.
  3. The install layer runs: four packages, tens of seconds. Cached from here on.
  4. Three .py files copied. appuser created, then the process drops to it.
  5. Now edit step6_service.py and rebuild: Docker reuses everything through the install and redoes only the copy onward. About a second — the payoff of the ordering.
  6. docker run --rm -p 8000:8000 -e ANTHROPIC_API_KEY=... -e API_KEYS=dev-key-123 dorm-agent
  7. uvicorn binds 0.0.0.0:8000 inside; Docker maps it to your localhost:8000.
  8. Five seconds later the health check begins polling /health. docker ps shows (healthy).
  9. A request to /ask with the key header runs the agent. The JSON trace line reaches your terminal immediately — because of PYTHONUNBUFFERED.
  10. Omit -e API_KEYS and every request returns 503: the service fails closed rather than serving anonymously.

Traps

  • Build from inside samples/ (or pass samples/ as the context). The COPY paths are relative to the build context, not to the Dockerfile.
  • Both env vars are required at docker run. ANTHROPIC_API_KEY and API_KEYS. Missing the second gives 503 on every request — deliberate, not broken.
  • Never bake a key in with ENV. It would be in the image, in the layer history, and in your registry. Pass secrets at run time.
  • Deleting a file in a later layer doesn't remove it. Layers are additive — a secret copied in once is in the image forever. That's why COPY here names three files.
  • Minimum-version pins, not a lockfile. Two builds a month apart may not be identical.
  • python:3.12-slim is a moving tag. Pin a digest if you need reproducibility.
  • No step6b_governance.py in the image. Only the three files the service imports — the governance sample is a CLI demo, not part of the service.
  • The image needs no docker-compose or registry to try. It also has no logging driver, no resource limits, and no restart policy — all of which are the orchestrator's job.

What to watch when you run it

docker build -t dorm-agent . docker run --rm -p 8000:8000 -e ANTHROPIC_API_KEY=$env:ANTHROPIC_API_KEY -e API_KEYS=dev-key-123 dorm-agent curl -s localhost:8000/health curl -s localhost:8000/ask -H "content-type: application/json" -H "x-api-key: dev-key-123" -d "{\"question\":\"What are the quiet hours?\"}"

Watch for CACHED markers on the second build, and for the trace line appearing in the container's output the moment a request completes.

Predict before you build Edit one comment in step6_service.py and rebuild. How many of the layers rebuild — all of them, or two? And roughly how long? Guess a number, then time it.
Then break it twice, on purpose 1. Change --host 0.0.0.0 to --host 127.0.0.1, rebuild, run, and curl. You'll get a connection refused that looks exactly like a Docker networking fault and is nothing of the kind — it's the most common first-container bug, and meeting it deliberately is cheaper than meeting it at 6pm.

2. Move the COPY config.py ... line above the RUN uv pip install line, then edit a .py file and rebuild. Time it. That difference — one second against forty — is what "layer ordering" actually means, and you'll never need to look it up again.
