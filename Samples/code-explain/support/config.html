config.py

The file every other sample imports. Three things live here because all three change constantly and none of them should be scattered across a dozen files: which model, which provider, and what it costs.

What happens when you run it Nothing — it has no main. It's a module. But everything you run touches it, so a mistake here shows up as a puzzling failure somewhere else.

The one idea it teaches The model is a dependency, not a fact of nature. Treat it exactly like a database connection string: one place, environment-overridable, never hardcoded at the call site.

What it deliberately leaves out Retry policy, timeouts, and connection pooling — the SDK handles those. And the prices are a hardcoded snapshot that will go stale; the habit to build is "look it up", not "remember it".

2PRICES + cost_usd() — observability is just arithmetic

config.py:29-59

A price table per million tokens, and a function that turns a response's usage object into dollars.

CACHE_WRITE_MULTIPLIER = 1.25   # first call pays a premium to populate the cache
CACHE_READ_MULTIPLIER  = 0.10   # every later call reads it back at ~90% off

dollars = (fresh * price_in
           + cache_write * price_in * CACHE_WRITE_MULTIPLIER
           + cache_read  * price_in * CACHE_READ_MULTIPLIER
           + out * price_out)
ConceptCost attribution (module 6.2). There is no magic in it — four token counters and a multiplication.
Why input and output are priced separatelyOutput costs roughly five times input. That single fact reshapes design decisions: a verbose system prompt is cheap, a verbose answer is not, and "be concise" is a cost control as much as a style one.
Why cached input needs its own termThis is the part people get wrong. Cached tokens aren't free — they're about 10% of the input rate, and the first call pays 125% to populate the cache. So caching is a bet that you'll read the prefix back more than once or twice. Fold cached tokens into the normal input count and your dashboard will overstate cost by 10× on a cache-heavy workload.
Why getattr(usage, ..., 0) or 0Not every response carries every field — a call with no caching has no cache_read_input_tokens. The or 0 also catches an explicit None, which getattr's default would not. Defensive, and the alternative is an AttributeError inside your cost logger, which is a maddening place to have one.
Where it's actually usedstep6_service.py's Trace class calls this once per model call in the loop and sums it. That's how you discover one question is several billable calls.

3get_client() — the portability seam

config.py:75-110

Returns a client for whichever platform AI_PROVIDER names — first-party, Bedrock, Vertex, or Foundry.

if PROVIDER == "anthropic":
    return anthropic.AsyncAnthropic() if async_ else anthropic.Anthropic()

if PROVIDER == "bedrock":
    cls = _resolve("AnthropicBedrockMantle", async_)
    return cls(aws_region=os.environ.get("AWS_REGION", "us-east-1"))
ConceptA factory behind a stable interface. Every client returned exposes the same .messages.create() and .messages.stream().
Why this matters more than it looksEnterprise and government work almost never calls api.anthropic.com directly. It consumes AI through a procured platform, in a chosen region, under an existing contract. If your only skill is one vendor's SDK you're not portable to the jobs that exist — and the honest news is that the request body is essentially identical everywhere. Only the constructor and the credential source change. This function is that whole insight, made executable.
The gotcha the comments flagModel ids are not portable. Bedrock prefixes them (anthropic.claude-sonnet-5); Vertex uses bare or @-versioned ids. So swapping AI_PROVIDER alone isn't always enough — which is exactly the kind of thing you want to discover from a comment rather than a 404.
Why credentials aren't parametersEach branch pulls from that platform's normal chain: ANTHROPIC_API_KEY, the AWS chain, GCP application-default credentials. Passing secrets as function arguments invites them into a log line or a traceback. Let each platform's own mechanism own them.

4_resolve() — look it up, don't assume it

config.py:112-136

Finds a client class on the anthropic module by name, preferring the Async-prefixed variant, and raises a clear message if it isn't there.

if async_:
    async_cls = getattr(anthropic, f"Async{name}", None)
    if async_cls is not None:
        return async_cls
    raise SystemExit(f"This SDK version has no Async{name}. ...")
ConceptRuntime capability detection instead of a hardcoded assumption.
Why not just write the class nameThe async classes follow an Async-prefix convention, but SDK support varies by platform and version. Inventing a class name that doesn't exist is a worse failure than a clear message — you'd get an ImportError at the top of the file with no hint about which platform lacks support. This way the error names the missing class and suggests the workaround.
Why the error message tells you to run dir(anthropic)Because that's genuinely what you'd do next, and a good error message shortens the loop between failure and fix. The general habit worth taking: when a library's surface is uncertain, check it rather than guess — and let your code do the checking so the answer arrives at the moment it's needed.
Honest note on this blockThis is defensive plumbing, not a lesson about AI. Skim it. The one transferable idea is the error message quality.

5EFFORT and MAX_TOKENS_DEFAULT — the comment block that saves an afternoon

config.py:138-157

Two settings, and twelve lines of comment explaining why three familiar parameters are gone.

# temperature / top_p / top_k  -> 400 error if set to a non-default value
# thinking.budget_tokens       -> 400 error (replaced by adaptive thinking)
# assistant-turn prefill       -> 400 error

EFFORT = os.environ.get("AI_EFFORT", "high")
MAX_TOKENS_DEFAULT = 4096
Concepteffort is the modern dial — low through max — and it controls how much the model reasons, not how randomly it samples.
Why this comment lives in a config fileBecause it's the first thing you'll break. Every pre-2026 tutorial writes temperature=0, and on current models that request fails outright. Putting the warning next to the setting that replaced it means you meet it before you write the bug rather than after.
Why MAX_TOKENS_DEFAULT is 4096 and not 1024Adaptive thinking is on by default, and max_tokens caps thinking plus the answer together. A budget copied from an older tutorial now silently truncates mid-sentence — you get a stop_reason of max_tokens and an answer that just stops. Giving it room is cheaper than debugging it.
Choosing an effort levelhigh is the default and usually the sweet spot. low is right for narrow judgements — step3b's reranker and evals.py's judge both use it. Reserve the top settings for work where correctness genuinely outweighs cost, not as a reflex.

Traced end to end

What happens when step3_agent.py starts, with nothing set in your shell.

  1. from config import EFFORT, MODEL, get_client executes this module top to bottom.
  2. AI_MODEL is unset → MODEL = "claude-sonnet-5".
  3. AI_PROVIDER is unset → PROVIDER = "anthropic".
  4. AI_EFFORT is unset → EFFORT = "high".
  5. step3 calls get_client(async_=True) → first branch → anthropic.AsyncAnthropic(), which finds ANTHROPIC_API_KEY itself.
  6. Every model call in the loop passes model=MODEL and output_config={"effort": EFFORT}. Nothing in step3 names a model or a provider.
  7. Now set $env:AI_MODEL = "claude-haiku-4-5" and re-run. Every sample switches. That's the payoff.

Traps

  • The prices are a snapshot and they go stale. Treat cost_usd() as an order-of-magnitude tool, and check current pricing before you quote a figure to anyone.
  • A model missing from PRICES costs $0.00. PRICES.get(model, (0.0, 0.0)) fails quietly — override AI_MODEL to something not in the table and your traces cheerfully report free. This is the one genuine sharp edge in the file.
  • Token counts aren't comparable across model generations. Tokenizers change; the same text can be ~30% more tokens on a newer model. Re-count against the model you're shipping.
  • Bedrock and Vertex need their own model-id formats and their own credentials. Switching AI_PROVIDER is necessary but not always sufficient.
  • Env vars are read at import time. Setting one after the module loads does nothing — set it before launching, which matters most for uvicorn.
  • Nothing here validates AI_EFFORT. A typo like "higj" reaches the API and comes back as a 400.

What to watch when you run it

It has no main, so exercise it through another sample:

uv run --with anthropic step3_agent.py "What are the quiet hours?" $env:AI_MODEL = "claude-haiku-4-5" uv run --with anthropic step3_agent.py "What are the quiet hours?"
Predict before you run Switching to the cheapest model: will the agent still get the answer right? Will it use the same number of tool calls? One of those two is much more likely to change than the other — guess which, then check.
Then do the arithmetic that is most of cost engineering Open PRICES. A 20-turn conversation where history reaches ~8,000 input tokens by the end averages roughly 4,000 input and 300 output tokens per turn. Work out the total at each of the three tiers, then decide which tier each sample in this repo should actually use. That calculation — not a framework — is what "right-sizing the model" means in practice.
