evals.py

The file that turns "it feels right" into a number. Twelve cases, two graders, one pass rate — and it's the same module you run by hand and the CI gate runs on every pull request.

What happens when you run it Nothing directly — it has no main. step5_orchestrator.py imports it and calls run_suite(), which prints a PASS/FAIL line per case and a final pass rate.

The one idea it teaches Use the cheapest grader that can do the job. Eight cases here are graded by a free substring check; four need a model because no assertion can express what they're testing.

What it deliberately leaves out Trace-based grading (did it call the right tools, not just reach the right answer), any check of the judge's agreement with a human, and a held-out set you never tune against. Twelve cases is a starting point, not a suite.

Twelve dictionaries. Each has a question, the subtasks the orchestrator should fan out, and either an expect substring or a rubric.

ConceptAn eval set — a regression test for behaviour, not for code correctness. Your unit tests can all pass while the agent gets worse.
Why this list is worth more than the 60 lines of machinery below itThe graders are generic; you could copy them from anywhere. This list is domain knowledge, and it's the part almost nobody writes. Twelve cases took perhaps half an hour and they're what makes every later change measurable instead of hopeful.
Why id mattersSo a failure is reportable. [FAIL] grounding-unknown-block tells you what broke; [FAIL] case 10 tells you to go counting. Ids also survive reordering, which "case 10" doesn't.
Read the comments on the awkward casesThey record why each case exists. comparison carries a note explaining that a substring check would pass for the wrong reason; the two grounding-* cases explain that the correct answer is a refusal. Six months from now that reasoning is the difference between maintaining the suite and rewriting it.

2The case a substring check gets wrong

evals.py:86-95

"Which block has more residents, Dorm A or Dorm B?" — deliberately given a rubric and no expect.

# No `expect`: "Dorm A" could appear in a wrong answer too, so a
# substring check would pass for the wrong reason. Judge it instead.
"rubric": "The answer must state that Dorm A has more residents than Dorm B. ..."
ConceptA substring check can verify a fact. It cannot verify a relation.
Work the trap throughGrade this with "Dorm A" in answer. Now consider the answer "Dorm B has more residents than Dorm A." — the exactly-wrong answer. It contains the string. It passes. You now have a green test protecting a bug, which is worse than no test, because it buys false confidence in precisely the place you were trying to be careful.
The general ruleIf the answer's correctness depends on structure — ordering, comparison, negation, "both X and Y" — a substring check is the wrong tool. Reach for the judge. If correctness is "does this specific number appear", don't.

3The refusal cases — the most valuable in the suite

evals.py:96-114

Two cases that ask about things the knowledge base doesn't contain: a Dorm Z, and rent. Passing means declining to answer.

"rubric": "The knowledge base contains no information about Dorm Z. The answer
           PASSES only if it says the information is not available / unknown /
           not in the documents. It FAILS if it states any resident count for
           Dorm Z, even a hedged one."
ConceptTesting for a negative. An agent's real reliability lives in what it refuses to say.
Why an assertion genuinely cannot do thisYou'd have to assert the absence of every possible fabricated number, phrased any number of ways — "around 400", "approximately 350 residents", "I'd estimate 300". There is no string to match on, because the failure mode is generative. Only something that understands the answer can grade it.
Why "even a hedged one" is in the rubricBecause a hedge is the failure. "I don't have exact figures, but Dorm Z likely houses around 400 residents" sounds responsible and is a fabrication that will end up in a spreadsheet. Spell out that hedged inventions fail, or the judge will accept them — they read as appropriately cautious.
Why these two cases earn their costThey're the ones most likely to silently regress when someone "improves" a prompt. Delete the line "say so plainly rather than guessing" from step3_agent.py's system prompt and watch these flip while everything else stays green. That's a regression no unit test would ever catch — and it's the first thing a careful interviewer probes.

4grade() — the routing is one if

evals.py:127-152

Uses the substring check when the case has expect; otherwise calls the model with the rubric.

if "expect" in case:
    ok = case["expect"] in answer
    return ok, f"substring {case['expect']!r} {'found' if ok else 'MISSING'}"

response = await client.messages.parse(
    output_config={"effort": "low"},
    output_format=Verdict,
    system="You are a strict grader. Apply the rubric literally. When in
            doubt, fail the answer -- a false pass is far more expensive
            than a false fail.",
    ...)
ConceptLLM-as-judge, with two properties that make it trustworthy: it grades against a rubric, and it never sees which outcome you were hoping for.
Why the "when in doubt, fail" instructionBecause the two error types aren't symmetric. A false fail costs you five minutes reading a passing answer and shrugging. A false pass ships a regression. Tell the judge which way to lean, or it will default to being agreeable — models are trained to be helpful, and "helpful" reads as generous marking.
Why the judge never learns the expected answerIt gets the question, the answer, and the rubric — nothing else. Show it the answer you wanted and you've built a similarity check with extra steps, which will happily pass anything phrased alike.
Why effort: "low""Does this answer meet this rubric?" is a narrow judgement, not a reasoning problem. High effort would cost more and change little. And a cheaper grader is one you'll keep running — which is the property that actually matters.
Why the return type is (bool, str)The string is the reason. [FAIL] comparison — judge: names Dorm B as larger tells you what happened; a bare False sends you re-running things by hand. When a gate fails in CI, that string is the whole report.

5run_suite() — concurrency, and crashes as failures

evals.py:154-173

Runs every case through the supplied answer function, four at a time, and returns (passed, total, rows).

sem = asyncio.Semaphore(concurrency)
...
try:
    answer = await answer_fn(case["q"], case["subtasks"])
except Exception as exc:            # a crash is a FAIL, not a stop
    return case["id"], False, f"raised {type(exc).__name__}: {exc}", ""
ConceptBounded concurrency (module 1.2's Semaphore, doing real work here), plus per-case error isolation.
Why a crash is a fail rather than an abortBecause you want the whole picture. If case 3 raises and takes the run down, you learn nothing about cases 4–12 and you'll fix one bug at a time across twelve runs. Catching per case turns a crash into a data point — and note the exception type ends up in the reason string, so it's still diagnosable.
Why the semaphore, rather than firing all twelveRate limits. Twelve concurrent orchestrator runs, each fanning out to several workers, is a lot of simultaneous calls. Four is a modest cap that keeps the suite fast without tripping limits — and this is the pattern from step1_mock_agent.py finally used for something real.
Why it takes answer_fn as a parameterSo the suite doesn't know what it's grading. Today it's the orchestrator; point it at the bare Step 3 agent and you can measure what the fan-out actually buys you. An eval suite coupled to one implementation can't answer comparison questions, which are most of the interesting ones.

6report() — and where the threshold lives

evals.py:176-184

Prints a line per case, echoes the answer for failures only, and returns the pass rate as a float.

ConceptSeparation of reporting from gating. This function returns a number; the caller decides what to do about it.
Why the answer is echoed only on failureBecause on a green run it's noise, and on a red one it's the first thing you need. Printing everything means nobody reads any of it.
Why the threshold isn't herestep5_orchestrator.py takes --threshold and exits non-zero below it; the CI workflow passes 0.75. Keeping policy out of the measuring instrument means you can tighten the gate without touching the suite — and different environments can hold different bars.
Why 0.75 and not 1.00Judge-graded suites have real variance. A 100% gate fails on an unrelated PR, gets re-run, passes, and within a fortnight someone marks it non-blocking — and then you have no gate at all. Set the bar just under your current rate and ratchet it up. A gate that flakes gets disabled; a gate that catches real regressions gets trusted.

Traced end to end

One case: grounding-unknown-block — "How many residents live in Dorm Z?"

  1. run_suite(orchestrate) acquires a semaphore slot and calls orchestrate(q, subtasks).
  2. The orchestrator fans out one worker with the same question. The Step 3 agent calls search("residents Dorm Z").
  3. The keyword store finds nothing matching "Z" → "no matching documents".
  4. The agent's system prompt says to answer only from returned documents and say so plainly otherwise — so it reports it has no information about Dorm Z.
  5. Synthesis carries that through; its prompt also forbids filling gaps.
  6. grade() finds no expect → judge branch. It sends question, answer, and rubric — and no hint of the desired outcome.
  7. The judge returns Verdict(passed=True, reason="declines to give a figure and says the data is unavailable").
  8. [PASS] grounding-unknown-block judge: declines to give a figure...
  9. Now the counterfactual: had the agent guessed "roughly 400", the rubric's "even a hedged one" clause fails it — and that's the single most useful failure this suite can produce.

Traps

  • Two cases pass by refusing. A confident numeric answer for Dorm Z or for rent is a FAIL. If you're skimming output, those two lines read backwards.
  • Judge-graded cases can flip between runs. Borderline answers land differently. Don't treat a single run as a measurement — that variance is exactly why the gate isn't at 100%.
  • Twelve orchestrator runs cost real money, each fanning out to workers, plus four judge calls. Cheap, not free — and it's why the CI workflow has a paths filter.
  • A case with neither expect nor rubric would crash the judge branch with a KeyError. Nothing validates the suite's own shape; if you add a case, give it one or the other.
  • expect wins when both are present. The if checks expect first, so a rubric alongside it is silently ignored.
  • The suite tunes and tests on the same cases. Real practice keeps a held-out set you never look at while iterating — not modelled here.
  • Nothing checks the judge against a human. On a suite you depend on, you'd sample its verdicts and confirm you agree.
  • No main. Run it via step5_orchestrator.py. Needs ANTHROPIC_API_KEY, anthropic, pydantic.

What to watch when you run it

uv run --with "anthropic,pydantic" step5_orchestrator.py

Watch which cases fail and what the reason string says. A judge failure with a good reason is far more informative than a substring miss.

Predict before you run Which of the twelve is most likely to fail? Most people guess an arithmetic case. The refusal cases are usually the fragile ones, because they depend on a single line of the system prompt holding. Guess, then look.
Then cause a regression on purpose — this is the exercise Open step3_agent.py and delete "if the documents do not contain the answer, say so plainly rather than guessing" from SYSTEM. Re-run the suite.

The arithmetic cases stay green. The grounding-* cases go red. You just watched a one-line prompt edit break behaviour with no error, no stack trace, and no failing unit test — caught only because twelve cases were sitting there. That is the entire argument for module 5.4, and for the CI gate in 6.6.
