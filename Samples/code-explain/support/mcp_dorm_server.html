mcp_dorm_server.py

52 lines, two tools, no magic. This is the thing you'll usually consume rather than write — and it exists mainly so you can see there's nothing intimidating inside one.

What happens when you run it Almost nothing visible. It waits on standard input for a client to speak to it, and looks hung. That is correct behaviour, not a bug — step5b_mcp_client.py launches it as a subprocess.

The one idea it teaches A tool definition and a tool implementation can be the same object. The decorator turns your function signature into the schema and your docstring into the description.

What it deliberately leaves out Everything that makes a server production-worthy: no auth, no rate limiting, no input validation beyond the type hints, no remote transport, and a keyword search barely worth the name.

2@mcp.tool() — the only interesting line in the file

mcp_dorm_server.py:30-43

Registers a plain function as a tool, deriving its schema from the signature and its description from the docstring.

@mcp.tool()
def search_dorm_facts(query: str) -> str:
    """Search the dormitory knowledge base for facts about blocks and rules.

    Args:
        query: Words to look for, e.g. "Dorm A residents" or "quiet hours".
    """
ConceptIntrospection as configuration. query: str becomes {"type": "string"}; the docstring becomes the text the model reads when deciding whether to call this.
Why this beats writing the schema by handOpen step3_agent.py's TOOL_SCHEMAS: a registry dict and a parallel list of hand-written JSON Schema, kept in sync by hand. Add a tool to one and forget the other and either the model doesn't know it exists, or a call arrives and hits a KeyError. Here there's one source of truth. The walkthrough for step3 calls that duplication a rough edge — this is what fixing it looks like.
Why the docstring is load-bearing, not documentationIt's the only thing the model has to decide whether this tool is relevant. A vague one-liner produces a tool that gets ignored or misused. That's why this docstring includes examples of what to pass — "Dorm A residents", "quiet hours". Write tool docstrings for the model, not for the next developer, and note this is module 1.3's "the description is sent to the LLM" lesson in a different costume.
The Step 1 drill was pointing here all alongstep1_mock_agent.py asked you to extend register_tool so it captured each function's docstring and signature into a schema dict via inspect. That's precisely what this decorator does. You built the toy version before meeting the standardised one.

3The two tools — deliberately unimpressive

mcp_dorm_server.py:37-48

search_dorm_facts does naive word-overlap over three strings. list_blocks returns the dict keys starting with dorm-.

Why the search is bad on purposeIt's the same naive overlap that step3b_retrieval.py measures at recall@1 of 0.46. Nothing about MCP improves retrieval quality — a protocol moves a function call across a process boundary, it doesn't make the function better. Worth being clear about, because "we exposed it over MCP" is sometimes said as though it were an upgrade.
Why there are two tools and not oneSo the client can demonstrate a choice. Ask "how many residents in Dorm A?" and the model picks search_dorm_facts; ask "list every block" and it picks list_blocks — a decision nothing in the client code influences, made purely from the two descriptions.
list_blocks() -> list[str] with no argumentsA tool needn't take input. The return annotation still matters: it tells the client what shape comes back. Cheap detail, easy to omit, and omitting it makes the tool harder for the model to use well.

4mcp.run() — and why the silence is correct

mcp_dorm_server.py:51-52

if __name__ == "__main__":
    mcp.run()          # stdio transport -- the client spawns us and talks over pipes
Conceptstdio transport. The client launches this as a child process and speaks the protocol over its stdin/stdout — the same mechanism a shell pipeline uses.
Why you must never print() in an MCP serverBecause stdout is the protocol channel. A stray print() injects garbage into the message stream and the client's parser fails — usually with an error that says nothing about your print statement. If you need to log from a stdio server, log to stderr or to a file. This is the single most common way to break one, and the reason this file prints nothing at all.
Why running it directly looks brokenIt blocks waiting for a client on stdin. No banner, no port, no output. Correct, and confusing the first time — which is why the module docstring says so explicitly.
What changes for a remote serverOnly the transport. The tools and decorators stay identical; you'd swap stdio for HTTP and then genuinely need the auth, rate limiting and input validation this file has none of. A local stdio server you launch yourself and a remote one you connect to have very different threat models, even though the code looks the same.

Traced end to end

What this process experiences during one client run.

  1. step5b spawns python mcp_dorm_server.py. Import runs; @mcp.tool() registers both functions into the FastMCP instance.
  2. mcp.run() blocks on stdin. Nothing is printed.
  3. An initialize message arrives; the server replies with its name and capabilities.
  4. A list_tools request arrives. The server serialises both registered tools — names, generated schemas, docstring descriptions — and writes them to stdout.
  5. A call_tool request arrives for search_dorm_facts with {"query": "Dorm A Dorm B residents"}.
  6. The arguments are validated against the generated schema, then the plain Python function runs: split, filter words over two characters, match against DOCS.
  7. Two matching lines are returned as one string, serialised back over stdout.
  8. The client finishes and closes the pipes. This process exits — its lifetime was entirely the client's async with block.

Traps

  • Running it directly looks hung. It's waiting for a client on stdin. Not a bug — press Ctrl+C.
  • Never print() here. stdout is the protocol. Use stderr or a file if you must log.
  • Needs the mcp package and Python 3.10+. uv run --with mcp mcp_dorm_server.py only proves it imports.
  • Launched with a relative path by the client, so both must run from inside samples/.
  • Zero security. No auth, no rate limiting, no authorisation on list_blocks. Fine for a local subprocess you wrote; not a template for anything reachable.
  • The search is genuinely poor — naive word overlap, no ranking. Deliberate: it's the baseline step3b measures.
  • Needs no API key. It never talks to a model — it's a tool provider, not a client.

What to watch when you run it

Don't run it directly — run the client and watch what it discovers:

uv run --with "anthropic[mcp],mcp" step5b_mcp_client.py

The tools discovered from the server list is this file's docstrings and signatures, round-tripped through the protocol.

Predict before you run The client prints each tool's description. Where does the text come from — a config file, a schema you wrote, or something already in this file? And will the Args: section appear in it?
Then prove the protocol claim — the whole point of this file Add a third tool here:
@mcp.tool()
def count_residents(block: str) -> str: with a docstring, returning whatever DOCS.get(block) gives.

Now re-run the client, unchanged. It appears in the discovered list and the model will use it. Then count what the same addition costs in step3_agent.py: a function, a TOOLS entry, and a hand-written JSON schema kept in sync. That difference is the value of a protocol boundary — and you've now measured it rather than read about it.
