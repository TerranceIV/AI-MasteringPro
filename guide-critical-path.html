What changed, and why

  • 5.4 Evaluation ○→★★★. It was already called "what separates hobbyist from professional" — that deserves three stars, not two. It's also the one skill that makes every other number on your CV credible.
  • 3.3 RAG ○ → 3.3a + 3.3b, both ★★. The anti-hype instinct was right; the conclusion overshot. See below.
  • 5.3 MCP ○→★★ for consuming, ○ for authoring. The old page said "skim" while the finish page said "learn it deeply." Now it says one thing.
  • 2.4 ○→★★. Promoted purely because getting it wrong is a hard 400 error, not a quality issue.
  • 6.5 and 6.6 ○→★★. Both had running code that didn't match what the capstone promised. Now they do, and both are cheap.
  • 6.7 is new and goes straight to ★★★ — for you specifically. See "Your leverage."

Lower value than the hype suggests

These get the most attention online and deserve the least of your depth.

  • Multi-agent orchestration — heavily over-hyped. Most production systems that actually work are one good agent with good tools. Learn the patterns; resist reaching for them.
  • Framework depth — commoditized and churns yearly. Learn one well enough to ship; don't invest identity in it.
  • Vector databases — not retrieval itself. The field did shift toward long context, and a vector DB is the most expensive fix you can reach for. Beat a plain lexical baseline first; add embeddings only when you can name the queries that demonstrably fail without them (that's 3.3b).
  • Fine-tuning — you almost certainly never need it. Prompting + tools + retrieval cover nearly everything. Revisit only when your eval set shows a consistent format or style failure that prompting can't fix.
  • Agent frameworks as an identity — "LangChain developer" is not a career. "I understand the loop" is.

The one call this page got wrong

The earlier version marked RAG as skim, "hype ≠ value" — and then the finish page made a RAG chatbot the first portfolio project. Both halves can't be right.

The correction: the anti-hype instinct was sound but the conclusion overshot. Long context changes how much you retrieve and what you retrieve; it doesn't remove the need to find the right twenty pages out of two hundred thousand, and it does nothing for permissions, freshness, or citations. Enterprise AI work is overwhelmingly "answer questions over our documents."

So retrieval is now ★★, split into finding documents (3.3a) and measuring whether you found them (3.3b). The genuinely over-hyped part — reaching for a vector database as step one — stays in the list above. The under-rated part is that most "the agent hallucinated" bugs are actually retrieval misses, and ten labelled queries will tell you which you have.

Your leverage — where you're not a generic learner

That changes two things.

C# is your delivery vehicle

Microsoft.Extensions.AI and Semantic Kernel aren't a footnote for you — they're likely how you'd actually ship AI at work. Treat Python as the learning vehicle and C# as the delivery one. Every map carries a "⇄ Coming from .NET?" bridge for exactly this.

Related: 2.8 exists because a government project almost certainly won't call api.anthropic.com directly — it'll consume AI through a procured platform in a permitted region. Learning one vendor's SDK isn't portable to the job you actually have.

Governance is the differentiator — and now it's taught

In a government/PII context, "I can build an agent" is common; "I can build one that won't leak data or get hijacked" is rare. Your existing instincts — input validation, layered architecture, audit trails — transfer directly and are an advantage most AI-curious devs don't have.

This page used to assert that and then teach nothing about it. Module 6.7 now closes the gap: redaction before the model call, a hash-chained audit trail, approval gates on write tools, and a retention policy. Run step6b_governance.py --offline — it costs nothing and it is the most differentiating twenty minutes in the whole track for you.
