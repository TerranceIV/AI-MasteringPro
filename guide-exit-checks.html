Assessment · 6 exit checks + 2 rebuild drills

Exit Checks

Every other page in this track is input. This one is the only output. Five questions per step, answers hidden until you commit to a guess — plus the two drills that actually decide whether you learned it.

Why this page exists. Reading code you understand feels identical to being able to write it — right up until the moment you can't. That illusion is the single biggest failure mode in self-taught engineering, and ticking a checkbox does nothing to break it. Every question below is "predict what this does" rather than "define this term", because recall of a definition is not the skill you're building. Guess out loud before you open the answer. A wrong guess you committed to teaches you far more than a right answer you read.
Scoring: 4 out of 5 to move on. Under that, don't re-read the map — go run the sample and break it on purpose. Every question here corresponds to something you can make happen in samples/ in under two minutes.

01 Python Fluency

All five are things that will silently break an agent rather than raise an obvious error.

1What does the second call print?
def add(item, bucket=[]):
    bucket.append(item)
    return bucket

print(add("a"))
print(add("b"))
['a'] then ['a', 'b'] — not ['b']. Why: the default list is created once, when the function is defined, and shared by every call that doesn't pass one. In agent code this shows up as conversation history from one request leaking into the next. Default to None and build the list inside.
2What does this print?
fns = [lambda: i for i in range(3)]
print([f() for f in fns])
[2, 2, 2]. Why: closures capture the variable, not its value at creation time — so all three lambdas see the final i. This bites when you build a tool registry in a loop and every entry ends up pointing at the last tool. Fix with a default argument: lambda i=i: i.
3Three tool calls run under asyncio.gather(). The second raises. What happens to the first and third?
They're cancelled, and gather re-raises the exception — you lose the results of work that succeeded. Why it matters: one flaky tool takes down the whole turn. Pass return_exceptions=True and you get a list where failures are exception objects you can inspect and feed back to the model as tool_result with is_error. That's the difference between an agent that recovers and one that dies.
4Why does time.sleep(1) inside an async def make ten concurrent calls take ten seconds instead of one?
Because time.sleep blocks the event loop thread. Nothing else can run — not the other nine coroutines, not the web server, nothing. Why it matters: this is the #1 async bug, and it produces no error — just mysteriously serial performance. The same trap applies to requests.get() inside async code. Use asyncio.sleep and an async HTTP client. An await is the only place the loop can switch tasks.
5You have class Q(BaseModel): units: Literal["c","f"]. The model sends {"units": "x"}. What happens, and why is that good?
model_validate raises ValidationError — before your tool function ever runs. Why it's good: the model will occasionally send arguments outside your schema, and you want that caught at the boundary rather than deep inside your tool. Catch it, format it as a tool_result with is_error=True, and the model usually corrects itself on the next turn. step1_mock_agent.py does this on purpose — that ERROR: bad args line is the lesson, not a bug.

02 LLM Fundamentals

Questions 1–3 are the ones that will actually cost you an afternoon.

1You copy a snippet from a 2024 blog post and run it against claude-sonnet-5:
client.messages.create(model=MODEL, temperature=0, ...)
What happens?
A 400 error. Current models reject temperature, top_p and top_k when set to a non-default value. What to do instead: delete the argument. Steer with the prompt, and control reasoning depth with output_config={"effort": "..."}. This is the single most common breakage when following older tutorials — and note it's a hard error, not degraded output, so at least it tells you.
2Why can print(msg.content[0].text) raise AttributeError?
Because content is a list of typed blocks, and with thinking enabled block 0 is often a thinking block, which has no .text. The habit: always filter by type — "".join(b.text for b in msg.content if b.type == "text"). Tool calls, images and documents arrive the same way. Indexing into content is a bug waiting for the day thinking gets switched on.
3Your extraction worked fine on an older model. You switch to a current one, keep max_tokens=1024, and now answers get cut off mid-sentence. Why?
Adaptive thinking is on by default, and max_tokens caps thinking + answer together. The model spends part of your 1024 tokens reasoning and runs out mid-answer. Check for it: stop_reason == "max_tokens". Fix by raising the budget (these samples use 4096). Turning thinking off is usually the wrong fix — on current models it also makes them noticeably less willing to reach for tools, which is fatal in an agent loop.
4You send the identical request twice. Are the two responses identical?
No, and you can't make them so. Why it matters: people used to reach for temperature=0 for "determinism" — it never guaranteed identical output, and it isn't available now anyway. If you need stability, get it from structure (constrain the output to a schema so the shape is guaranteed) and from evals (assert on the facts you care about, not on an exact string). Never write a test that compares model output to a golden string.
5You counted a prompt at 1,000 tokens last year and sized your context budget around it. Why re-count today?
Tokenizers change between model generations. The same text can produce ~30% more tokens on a current model than on the previous one. Consequences: your context window holds less text than you think, a max_tokens tuned earlier may truncate, and your cost-per-request baseline shifts even when the per-token price hasn't moved. Always run count_tokens against the model you're actually shipping — never reuse a number measured elsewhere.

03 Agent Building Blocks

The keystone step. If you get fewer than 4 here, go back — everything after this assumes it.

1In the loop, you run the tool and append the tool_result — but forget to append the assistant message containing the tool_use block. What happens?
The API rejects it: a tool_result must reference a tool_use that exists in the conversation. Its tool_use_id now points at nothing. The mental model: the API is stateless. It has no memory of the turn it just produced — the conversation exists only in the array you resend. If you don't append it, it didn't happen.
2The model requests two tools in one turn. You send back two separate user messages, one result each. It's accepted — so what's the problem?
You've quietly taught the model to stop making parallel tool calls. It sees a history where simultaneous requests weren't answered simultaneously, and it degrades to one tool at a time. Why it's nasty: no error, no warning — just an agent that gets slower and more expensive over long conversations, for reasons that don't show up anywhere. Always return every tool_result from one assistant turn in a single user message.
3MAX_STEPS is 6 and the loop exhausts it. What does the caller get, and what should it get?
In step3_agent.py it returns the string "stopped: hit MAX_STEPS without a final answer" — a successful return carrying a failure. Why that's a problem in production: the caller can't distinguish "the agent answered" from "the agent gave up" without string-matching. Real systems raise, or return a typed result with a status field, so the failure is visible to monitoring. And you must cap the loop regardless — an uncapped agent loop is an uncapped bill.
4Your tool raises. You catch it and return the message as a normal tool_result without setting is_error. What does the model do?
It may treat your error string as data — and reason about, or report, "ERROR: division by zero" as though it were a legitimate result. The distinction: is_error=True tells the model the call failed so it can retry differently or explain the limitation. And the broader judgement call from module 1.5 sits here: some failures are recoverable (feed them back) and some are fatal (stop the loop). Feeding back a fatal error just burns tokens on six doomed retries.
5You add cache_control to the system prompt, run the agent, and cache_read_input_tokens is 0 on every turn. Is caching broken?
No — the prefix is almost certainly too short. Caching needs roughly 1024+ tokens before it engages, and it fails silently below that. The real lesson: that counter is how you verify caching instead of assuming it. If it's zero on a genuinely large prefix, hunt for a silent invalidator — a timestamp or UUID in the system prompt, unsorted json.dumps, or a tool list whose order varies. Caching is a prefix match: one changed byte early invalidates everything after it.

04 Frameworks

The lightest step. These are judgement questions, not trivia — there's no syntax to memorise here.

1Name four things create_react_agent does that you wrote by hand in Step 3.
The while-loop and its step cap; tool dispatch and tool_result plumbing; stop_reason handling; and message-history bookkeeping. Why the order matters: you can only evaluate what a framework hides once you've written it. That's the entire reason Step 3 comes before Step 4 — otherwise the framework isn't an abstraction, it's a black box you're superstitious about.
2step4_langgraph_agent.py passes max_tokens=4096, not 1024. Why won't the framework tell you that matters?
Because it's a fact about the model (thinking shares the token budget), not about the framework. The abstraction has no opinion on it and passes your value straight through. The general lesson: frameworks abstract plumbing, never model behaviour. Truncation, refusals, injection, cost, tokenizer changes — all still yours. This is the class of bug that abstraction hides rather than solves, and it's why Step 2 isn't optional.
3A framework release changes its agent API and breaks your app. What limits the damage?
That you can drop back to the raw loop — plus keeping the framework at the edges of your system rather than letting its types spread through your domain code. The posture: learn one framework well enough to ship, don't invest your identity in it. "I understand the loop" survives version churn; "I'm a LangChain developer" doesn't. Your prompts, tool schemas and eval set are the durable assets — none of them are framework-specific.
4When is a framework the wrong choice?
When your control flow is simple enough that the framework is most of your complexity; when you need behaviour it doesn't expose; when you can't afford to debug through its abstraction; or when its dependency footprint is a problem — a security-reviewed environment being the obvious case. Worth noticing: step3_agent.py is a complete, production-shaped agent in about 60 lines with one dependency. That's often the right answer, and it's a genuinely legitimate architectural position — not laziness.
5Your framework-built agent gives a wrong answer. Where do you look first?
The trace — the actual sequence of model calls, tool calls and results. Not the framework's source, and not the prompt. Why: agent failures are nearly always visible in the trace as a specific wrong step: a tool that returned nothing, a retrieval that missed, a truncated turn. This is why observability (6.1) is a debugging tool first and a monitoring tool second — and why "my agent is bad" is not a diagnosis.

05 Multi-Agent & Evaluation

Questions 2–5 are about eval, because that's where the value in this step is.

1Three workers, each taking ~3 seconds, run under asyncio.gather(). Total wall-clock? And if the worker were synchronous?
About 3 seconds concurrently; about 9 if the worker blocks. The connection to Step 3: this only works because the agent loop is async all the way down. Make it synchronous and you either serialise, or you paper over it with asyncio.to_thread — which works but caps you at the thread pool and hides a design flaw. Async at the bottom is what makes fan-out free at the top.
2Eval case: "Which block has more residents, Dorm A or Dorm B?" Why is "Dorm A" in answer a bad grader?
Because "Dorm B has more residents than Dorm A" contains the string "Dorm A" and passes. The grader can't tell the right answer from the exactly-wrong one. The rule: substring checks are perfect for a specific fact ("800") and useless for a relation. When the answer's correctness depends on structure rather than a token, use a judge with an explicit rubric. That's precisely why this case in evals.py has a rubric and no expect.
3You want to test that the agent refuses to invent a resident count for a block that isn't in the knowledge base. Why can't an assertion do this?
Because you'd have to assert on the absence of every possible fabricated number, phrased any number of ways. There's no string to match. Why these are the most valuable cases you'll write: an agent's real reliability lives in what it declines to say, and refusal cases are the first thing a careful interviewer probes. They're also the cases most likely to silently regress when someone "improves" a prompt — which is exactly what the CI gate is for.
4Eight of the twelve cases in evals.py use a free substring check rather than the judge. Why not judge everything?
Because the judge costs a call, adds latency, and introduces variance into your measuring instrument. The principle: use the cheapest grader that can do the job. A mostly-deterministic suite runs in seconds, never flakes, and therefore actually gets run — which is the only property that matters. A slow, expensive, flaky suite gets disabled within a fortnight, and then you have no gate at all.
5You set the CI gate at a 100% pass rate. Predict the next month.
It fails on an unrelated PR because a judge-graded case flipped. Someone re-runs it and it passes. That happens twice more, and then the gate gets marked non-blocking — and now you have no gate. The fix: set the bar just under your current pass rate and ratchet it up as the agent improves. A gate that flakes gets disabled; a gate that catches real regressions gets trusted. Judge-graded suites have irreducible variance — design for it instead of pretending otherwise.

06 Production & Governance

The employable layer. Questions 4 and 5 are the ones that distinguish you in a regulated environment.

1One user asks one question. Your trace line reports model_calls: 4. Bug?
No — that's the loop. Every iteration is a separate billable call, and each one re-sends the entire history. The consequence people miss: cost grows super-linearly with conversation length, because turn 5 pays for turns 1–4 again. That's why the right unit is cost per question, not cost per call — and why prompt caching on the stable prefix is the highest-leverage optimisation in an agent.
2Your SSE endpoint has streamed 200 tokens when the upstream call fails. Can you return a 500?
No. The status line and headers were sent before the first token. The response is already a 200. What to do: deliver the failure inside the stream — emit an error event and let the client render it. This is the mistake that turns a streaming endpoint into a client-side hang: the client sees a stream that simply stops and waits forever for a completion signal that never arrives.
3Your agent endpoint has no authentication. Beyond "unauthorised use", what specifically happens?
Anyone who finds the URL spends your API budget, at your rate limits — and each request runs a multi-call loop, so the cost per abusive request is high. It's the LLM equivalent of an open mail relay. And worse: they also get whatever your tools can reach. An unauthenticated endpoint over a retrieval store is an anonymous read API for your documents. One header check is the cheapest security control in the whole track.
4Someone edits one field in the middle of audit-log.jsonl. How is it detected — and what if they delete a whole line instead?
Each entry stores the hash of the previous one. Recomputing the chain fails at the edited line (entry was modified), and a deletion breaks the prev_hash link at the following line (chain break). Either way you get the exact line number. Why this is the point: it's about twenty lines of code, and it upgrades your logs from "records" to "evidence". Note the detail that makes it work: hashing over sorted JSON. Hash unordered output and the chain can't be recomputed — and a chain you can't verify proves nothing at all.
5An approval token for a write action gets submitted twice. What must happen, and why is redaction-before-the-call better than redaction-in-the-logs?
The second submission must be rejected and recorded — tokens are single-use, or a replay becomes a second write. And the approval must be persisted in the same transaction as the write, or you get an "approved but never applied" state nobody notices. On redaction: stripping PII before the model call means the answer to "what personal data left our boundary?" is none — provably, by construction. Redacting only in your logs still sent it to a third party; you've just made it harder to audit. The strongest control is the one that makes the data never exist in that path.

★ The two drills that actually count

The questions above test understanding. These test ability — and they are the only things on this page that can't be passed by recognition.

Drill A · Rebuild the agent from a blank file — after Step 3

Do this the day after you finish Step 3, not the same day.

  1. Move step3_agent.py somewhere you can't see it. Close the map.
  2. Open an empty file. Set a 45-minute timer.
  3. Write an async agent: two tools with schemas, the loop, concurrent tool dispatch, all results in one user message, a step cap, and errors fed back with is_error.
  4. Run it. Fix it until it answers "Total residents across Dorm A and B?" correctly.
  5. Only then diff yours against the original.

Pass: it works, and the diff is style rather than substance. Partial: you needed to peek once or twice — note exactly what for, that's your weak spot. Fail: you couldn't start. That's not a disaster, it's information: you had recognition, not recall. Re-run the sample, change things, break it, then retry the drill in three days.

Why 45 minutes and why from blank: nothing else discriminates between "I've read this" and "I can build this." If you can produce the agent loop from nothing, every framework, every orchestration pattern and every job interview in this field becomes vocabulary on top of something you own.

Drill B · Rebuild the service layer — after Step 6

Same rules, 60 minutes, starting from a working Step 3 agent you may keep.

  1. An authenticated POST /ask that rejects a missing or wrong key.
  2. A trace per request: request id, model-call count, tokens, and dollars.
  3. A timeout, so a stuck agent can't hold the connection open.
  4. An SSE endpoint that streams deltas and delivers a mid-stream failure inside the stream.
  5. An audit line per request that stores a hash of the question, never the text.

Pass: you can curl all of it, and docker build succeeds. If you can do this from memory you can put "I ship agent services" in writing and defend it — because most people claiming that have never done point 2 or point 5.

One honest caveat about this whole page. These checks only test what someone already thought to ask. They can't find the failure mode nobody anticipated — which is exactly the limitation of an eval suite, and the reason module 6.6 says every real production failure should come back as a new test case. Treat this page the same way: when something breaks for you that isn't covered here, add a question. A check-list that never grows is a check-list going stale.
