Plan audit · 20 Aug 2026

Is this plan comprehensive enough to train as an AI engineer?

An honest read of the six-step track as it stands today — 9 pages, 38 modules, 6 runnable capstones. The short answer: the spine is unusually good, and the perimeter is thin. You have built an excellent agent engineering curriculum and labelled it an AI engineering one. Those are not the same scope, and the difference is where the remaining work is.

As a path to “AI agent engineer”
Strong · ~85% → ~95%

The agent loop, tool use, context engineering and eval spine was better sequenced than most paid courses to begin with. What was missing was depth at the edges, not a rethink.

As a path to “AI engineer”
Partial · ~60% → ~85%

Was one provider, one modality, one deployment shape, retrieval optional. All four are now covered. What's still deliberately out of scope is listed in §5.

✔ All eight patches have been applied. The analysis below is preserved as the record of why — every gap, inconsistency and grade is the state of the plan before the fix, so the reasoning stays auditable. What changed is summarised immediately below; each gap in §4 and each inconsistency in §6 is now marked with its resolution. The original recommendation still stands, and is the most important line here: the plan didn't need restructuring. The six steps, the critical-path prioritisation and the build-raw-before-frameworks order were the hard parts, and they were already right. Everything below was perimeter work.

00What changed

Three new modules, two split, five re-rated, six contradictions removed — plus seven new runnable files and two live bugs fixed.

New curriculum · 38 → 42 modules

  • 2.8 Providers & model choice — Bedrock / Vertex / Foundry, model tiers, cost per 1M, residency.
  • 2.9 Documents & images — PDFs and scans as content blocks, straight into a validated object.
  • 6.7 Governance & auditability ★★★ — redaction, hash-chained audit trail, approval gates, retention.
  • 3.3 split into 3.3a + 3.3b, both promoted to ★★ — finding documents, and measuring whether you did.
  • 2.4 rewritten from “Sampling Controls” to “Effort & Thinking” — the old version taught an API that now 400s.

New code · 6 → 13 runnable files

  • step2b_document_extract.py — generates a real PDF, extracts a validated record, gates on confidence.
  • step3b_retrieval.py — naive vs BM25 vs BM25+rerank over 12 labelled queries.
  • step5b_mcp_client.py + mcp_dorm_server.py — runtime tool discovery over stdio.
  • step6b_governance.py — runs free with --offline.
  • evals.py — 12 cases, substring + judge, including two refusal tests.
  • Dockerfile, .github/workflows/eval.yml, .gitignore.
  • guide-exit-checks.html — 30 questions + 2 rebuild drills.

Two live bugs found while patching — the samples did not run as written

  • step2_first_call.py returned a 400. It passed temperature=0 against claude-sonnet-5, which rejects non-default sampling parameters. The Step 2 capstone — the first real API call in the whole track — could not have worked. Fixed, and module 2.4 was rewritten around exactly this failure.
  • max_tokens=1024 risked silent truncation everywhere. Adaptive thinking is on by default and max_tokens caps thinking plus answer, so the budget inherited from older tutorials can cut answers off mid-sentence. Raised to 4096 across the samples.

Neither was in the original audit — both surfaced only from checking the code against current API behaviour rather than reading it. Worth noting as a method point: an audit that only reads is an audit that misses whatever has rotted underneath.

02What this plan already gets right

Worth stating plainly, because the rest of this page is criticism and these six things are the reason the plan is worth patching rather than replacing.

The central insight is correct

“An agent is a while-loop plus tool dispatch” is the single most useful thing to understand about this field, and the whole track is organised around it. Most curricula bury this under a framework tutorial and the learner never sees the loop.

Raw first, framework second

Step 3 by hand → Step 4 in LangGraph is the right order and it is rare. It means a framework upgrade or a framework death never resets your skills. step4_langgraph_agent.py even lists what the framework hides.

One artifact, six steps

Step 5 and Step 6 literally import the Step 3 agent. Continuity like this is the highest-retention structure there is — nothing is a throwaway exercise.

Anti-hype calibration

Naming multi-agent orchestration and framework depth as over-hyped, and flagging context engineering as the under-rated craft, is a genuinely sharp read. Most plans do the opposite.

Deliberate failures as lessons

step1_mock_agent.py sends units:"x" so Pydantic rejects it; mock_call fails ~30% of the time to exercise backoff. Teaching through engineered failure is what separates a course from a tutorial.

It respects the expertise you have

The .NET bridges mean you are mapping new concepts onto Task-based async, Polly, DI and middleware rather than starting from zero. That is a real accelerant and most learners don't get it.

04The seven gaps that matter

Ranked by career impact × cost of learning it later. Each one carries the smallest fix that closes it — none of these require restructuring the six steps.

01

One provider, one model, one deployment target

highest impact

Every sample calls claude-sonnet-5 through the Anthropic SDK. config.py centralising the model id is good hygiene, but it centralises one vendor. There is nothing on Azure OpenAI, Bedrock, Vertex, a gateway like LiteLLM, or self-hosted open-weight models — and nothing on how to choose a model for a task, which is a question you will be asked in every interview and every architecture review.

Why this one is specifically yours: a Singapore government project will almost certainly not be calling api.anthropic.com directly. It will procure through a cloud provider's managed AI service, or require the model to stay inside a controlled boundary. Right now the plan teaches the one deployment shape you are least likely to be allowed to use at work.

Minimum fixAdd module 2.8 · Providers & model choice: the request shape is near-identical everywhere, so this is mostly a mapping exercise. Then refactor config.py from a model constant into a small client factory, and run step2_first_call.py once against a second provider. One evening of authoring; permanently removes vendor lock-in from your skill set.✔ Applied — module 2.8 added; config.py is now a provider factory (anthropic / bedrock / vertex / foundry) with a price table and a cost_usd() helper. Switch with $env:AI_PROVIDER.
02

No multimodal — text in, text out, only

highest impact

Searching all 25 files for image, vision, PDF, OCR or document returns nothing. Meanwhile the most common real-world AI request in an enterprise is some version of “read these thousands of documents and give me structured data.” Passing an image or a PDF page to a model and getting a validated Pydantic object back is a ~20-line skill that the plan currently never mentions.

Why this one is specifically yours: government work is document work — forms, scanned submissions, certificates, floor plans. This is likely the first genuinely useful AI thing you could ship at your job, and it is the cheapest gap on this list to close because it reuses 2.6 structured output verbatim.

Minimum fixAdd module 2.9 · Documents & images and one sample — step2b_document_extract.py — that sends a PDF page or screenshot and returns a validated model. Add a second sample step to the portfolio list: “a document-extraction agent.” Half a day.✔ Applied — module 2.9 added, plus step2b_document_extract.py, which generates a valid PDF from scratch so it runs with zero setup and gates on a confidence score. Now portfolio project #2.
03

Retrieval is under-weighted for the jobs that exist

high impact

3.3 RAG is marked ○ skim with “hype ≠ value,” and the critical path says one card is genuinely enough. The long-context argument behind that call is real — retrieval matters less than it did in 2023, and vector-DB obsession was a phase. But the conclusion overshoots. Long context changes what you retrieve and how much; it does not remove the need to find the right 20 pages out of 200,000, and it does nothing about permissions, freshness, or citation.

Specifically missing: hybrid search (keyword + vector — the single biggest quality win in practice), re-ranking, chunking strategy as a decision rather than a default, evaluating retrieval separately from generation (most “the agent hallucinated” bugs are actually retrieval misses), and where the corpus comes from and how it stays in sync.

Minimum fixPromote 3.3 from ○ to ★★ and split it into 3.3a retrieval quality (hybrid, re-rank, chunking) and 3.3b grounding & citation. Keep the anti-hype framing — the point isn't “vector DBs are back,” it's “retrieval quality is measurable and most people never measure it.” The step3_agent.py keyword store is a fine teaching stub; add a second version with hybrid scoring so the comparison is visible.✔ Applied — split into 3.3a (retrieval) and 3.3b (retrieval quality), both ★★. step3b_retrieval.py scores three retrievers over 12 labelled queries. The measured result is honest rather than flattering: naive@1 0.46 → BM25@1 0.71 → rerank ceiling 0.83, with 2 of 12 queries unreachable without embeddings. The anti-hype framing survived — the biggest win is the free one.
04

Your stated differentiator has no curriculum behind it

high impact

The critical-path page argues — correctly — that in a government/PII context, “I can build an agent” is common; “I can build one that won't leak data or get hijacked” is rare. That is the sharpest strategic insight in the whole plan. Then a search across all 25 files for governance, compliance, PDPA or GDPR returns one incidental hit. The differentiator is asserted and never taught.

What a governance module would actually contain: PII detection and redaction before the model call; an audit trail of prompts, completions, tool invocations and who triggered them, with a retention policy; data-residency and “can this text leave the boundary” decisions; least-privilege tool credentials scoped per user rather than per service; human-approval gates on write actions; and what you tell an auditor when they ask why the model said what it said.

Minimum fixAdd 6.7 · Governance & auditability as a full backbone module rated ★★★ — not a footnote. Extend step6_service.py with a redaction pass on input, a structured audit-log line per request (request id, user, tools called, tokens, cost, verdict), and one write-action approval gate. This is the highest-leverage single addition on this page for you specifically, because it converts an existing professional instinct into a demonstrable AI skill.✔ Applied — module 6.7 added as a ★★★ backbone module and rung 7 of the critical-path spine, plus step6b_governance.py: PII redaction before the call, a hash-chained tamper-evident audit log, single-use approval tokens on write tools, and a written retention/residency policy. Runs free with --offline. Tamper detection is verified — editing a line reports “line 3: entry was modified”, deleting one reports “line 2: chain break”.
05

“Production” stops short of production

medium-high impact

Step 6 is titled “the employable layer,” and its capstone promises five things: async endpoint, full tracing with per-run cost logging, prompt caching and right-sized models, input/output guardrails with least-privilege tools, and a CI eval gate. step6_service.py delivers two of the five — a guardrail pair and a timeout. There is no trace, no cost log, no caching, no CI config in the repo.

Also absent from the module list entirely: containerisation (zero mentions of Docker), authentication on the endpoint, streaming responses to a client over SSE or WebSocket (zero mentions), a job queue for runs longer than an HTTP timeout, per-tenant concurrency limits, and load testing. For a step whose whole claim is “I ship agents,” this is the thinnest part of the plan relative to its promise.

Minimum fixBring the sample up to its own capstone spec — add a tracing decorator that logs tokens and computed cost per run, prompt caching on the system prompt, an API-key dependency, and an SSE streaming endpoint. Add a Dockerfile and a GitHub Actions workflow that runs the Step 5 eval set and fails the build under a threshold. That single workflow file is the artifact that makes the “eval-gated CI” claim real.✔ Applied — step6_service.py now has API-key auth, a per-request trace line with tokens and dollars, an SSE streaming endpoint that delivers mid-stream failures inside the stream, and a timeout. Prompt caching moved into step3_agent.py. Added a Dockerfile (non-root user) and .github/workflows/eval.yml, which gates on a 0.75 pass rate and uploads the report on failure. Modules 6.1 and 6.5 rewritten to match.
06

MCP and the Agent SDK are taught but never run

medium impact

Two backbone modules have no runnable code anywhere in samples/: 4.3 Claude Agent SDK and 5.3 MCP. The Step 5 capstone is described as “orchestrator-worker system + MCP + eval set,” but step5_orchestrator.py contains no MCP at all. And the plan sends contradictory signals about how much MCP matters — the critical path marks it ○ skim, while the closing section of the production page says to “learn MCP deeply — it's the interoperability signal that stands out right now.”

Minimum fixPick one position on MCP and state it once. The defensible one: consuming MCP servers is ★★ and worth an hour; authoring one is ○ until you need to. Then add ~30 lines to step5_orchestrator.py that attach one existing MCP server as a tool source. That single change resolves both the missing sample and the contradiction, and it is the cheapest fix on this page.✔ Applied — the position is now stated once, in module 5.3: consuming is ★★, authoring is ○. Added step5b_mcp_client.py (discovers tools at runtime, hardcodes no schema) and mcp_dorm_server.py as the server to talk to. The finish-band line that said “learn MCP deeply” was rewritten to say what the actual signal is.
07

Nothing checks whether you actually learned it

structural

This is the gap that isn't about AI content at all, and it may be the one that decides whether the plan works. The track has 38 modules and 11 checkboxes. The only completion criterion anywhere is “if you can write this without googling every line, you're fluent enough to move on” — entirely self-assessed, at the exact moment when your judgement is least reliable. There is no recall test a week later, nothing that surfaces what you got wrong, and no external review of your code by anyone.

Evaluation as a topic has the same shape. 5.4 lists LLM-as-judge, trace-based grading and regression suites; the code is a two-case substring check. The plan correctly identifies eval as “what separates hobbyist from professional” and then models the hobbyist version.

Minimum fixThree cheap mechanisms. (a) A 5-question exit check per step with answers collapsed — write them as “predict what this code prints,” not recall questions. (b) A blank-file rebuild drill at Steps 3 and 6: delete the sample and rewrite it from memory, timed. That is the only test that reliably distinguishes recognition from ability. (c) One external checkpoint — publish the Step 3 agent and ask a real engineer to review it. Also grow the Step 5 eval set to ~10 cases with one LLM-as-judge grader, so the eval module practises what it preaches.✔ Applied — guide-exit-checks.html adds 30 “predict what this does” questions and the two blank-file rebuild drills, and START-HERE now asks for one external human review. evals.py grew to 12 cases with a rubric-driven judge, including two refusal cases a substring check cannot express. Module 5.4 promoted ○→★★★.

05What the plan is right to leave out

Comprehensive does not mean exhaustive. These omissions are correct — but say so on the page, so that “I skipped this deliberately” is available to you in an interview instead of a silent blank.

Fine-tuning and LoRA

Correctly dismissed in one line. Prompting, tools and retrieval cover nearly everything, and fine-tuning is a specialist move you make after evals prove you need it. Keep the dismissal, add the trigger: “revisit only when your eval set shows a consistent style or format failure that prompting can't fix.”

Transformers, attention, training, GPUs

Right to exclude — that is an ML-engineer or researcher path, not this one. The 2.1 black-box model is the correct level of abstraction. One paragraph of “what's inside the box and why you don't need it” would inoculate you against feeling under-qualified.

Classical ML, pandas, statistics

Right to exclude for an AI engineer title, and the plan already skips them explicitly in Step 1. Worth one honest sentence though: some job ads bundle both titles, so know the boundary you have drawn and be able to name it.

Deep multi-agent orchestration

The “most production systems that work are one good agent with good tools” framing is correct and unusually honest. Keep resisting it. The one thing to add is the counter-case: when the task genuinely has independent parallel subtasks, fan-out earns its cost — which the Step 5 sample already demonstrates.

06Six internal inconsistencies worth fixing

All verified against the files. These were cheap to fix and each one sent a mixed signal about what to prioritise. All six are now resolved — the resolution follows each item.

  • Async is rung 1 — and no real LLM call in the plan is async. The critical path says async is “where all agent performance comes from,” and step1_mock_agent.py is fully async. Then AsyncAnthropic never appears anywhere: step2 and step3 both use the sync client, and steps 5 and 6 work around it with asyncio.to_thread. step2_first_call.py even tags its streaming function as “(2.7 / 1.2)” — a cross-reference to the async module — on a plain def. The moment a real model appears, the plan's own keystone skill stops being practised. Fix: make step3's agent loop genuinely async and drop the to_thread workarounds downstream.
  • RAG is “skim” but it's portfolio project #1. critical-path marks 3.3 ○ with “hype ≠ value”; production-map makes a RAG chatbot the first of three portfolio pieces. Pick one — see Gap 3.
  • MCP is “skim” and also “learn it deeply.” Same two pages, directly opposed. See Gap 6.
  • The Step 6 capstone spec exceeds its own sample. Five bullets promised, two delivered. Either implement the other three or mark them as stretch items — right now the page implies the code exists.
  • Two timelines that differ by roughly 2×. See the arithmetic below.
  • Eval taught as rigour, demonstrated as a substring match. 2 cases, no judge, no regression file — while 5.4 lists LLM-as-judge and trace-based grading as its content.

✔ All six resolved:

  • Async — step3_agent.py is now genuinely async (AsyncAnthropic, concurrent tool dispatch via gather), step2's streaming uses async with / async for, and the to_thread workarounds in steps 5 and 6 are gone. Step 3's capstone spec and Step 5's exit check now both make the point explicitly.
  • RAG — promoted to ★★ and split; the critical path carries a short section admitting the original call overshot and explaining exactly which part of the anti-hype framing survives (reaching for a vector DB first).
  • MCP — one position, stated in 5.3: consume ★★, author ○.
  • Step 6 capstone — the sample now meets the spec, and the spec grew rather than shrank. A line was added noting that a spec your own repo doesn't meet is the most quietly corrosive thing in a learning project.
  • Timeline — see §7.
  • Eval — 12 cases, two graders, refusal tests, CI gate.

07Timeline reality check

The maps carry their own per-step estimates. Summing them contradicts the weekly rhythm on the start page.

Per-map "evenings" estimates:
  Step 1  Python Fluency        2–3 weeks
  Step 2  LLM Fundamentals      1–2 weeks
  Step 3  Building Blocks       3–4 weeks
  Step 4  Frameworks            2 weeks
  Step 5  Multi-Agent & MCP     3 weeks
  Step 6  Production            "ongoing"
                                ─────────────
  Steps 1–5 only               11–14 weeks
  + Step 6 + 3 portfolio projects        ≈ 5–8 months total

START-HERE weekly rhythm:
  Week 1     setup + Steps 1 & 2
  Week 2–3   Step 3
  Week 4+    Steps 4–6, then portfolio       ← implies ~6–8 weeks
  at 30–60 min/day

These can't both be true. The maps' own numbers are the credible ones; the START-HERE rhythm is roughly 2× optimistic, and Step 6 plus three portfolio projects is where most of the hidden time lives. This matters more than it looks — a plan that silently runs 3× its advertised length is the single most common reason self-directed tracks get abandoned around week 5, right at Step 3, which is the step you most need to finish.

Fix: state one honest number on START-HERE — “~4–6 months of evenings to the end of Step 6; the first portfolio project is where it starts paying” — and add a fourth rhythm card for months 2–4 so the road doesn't visibly end at “Week 4+”.

✔ Applied — START-HERE now leads with “about 4–6 months of evenings”, says plainly that an earlier version implied half that, and adds “You are not behind” next to the note that Step 3 alone is 3–4 weeks. The rhythm is four cards ending at Months 3–5, and there's a pointer to the 20% path for anyone who genuinely has weeks rather than months — because half-finishing every step is worse than fully finishing the five that matter. Step 2's own estimate also rose (3–4 days → 5–6) to account for the two new modules.

Still deliberately open

Named here so they're decisions rather than oversights. None blocks anything:

  • Voice / realtime audio — genuinely niche for this career target. Excluded on purpose.
  • Local / open-weight hosting (Ollama, vLLM) — 2.8 covers the portability question and names residency as a config concern, but there's no self-hosted sample. Worth adding only if your work actually requires the model inside your own boundary.
  • Data pipelines for retrieval at scale — where the corpus comes from, incremental sync, permissions following documents into the index. 3.3a flags the permission trap; the ingestion side is still a stub.
  • Job queues for long agent runs — 6.5 names it and the gotcha list covers it, but the sample returns synchronously rather than handing back a job id.
  • The C# delivery path — every map has a .NET bridge, but there's no runnable Semantic Kernel / Microsoft.Extensions.AI sample. Given that C# is the likely delivery vehicle, this is the most defensible next addition after finishing the track.
One last thing, and it's still the most important line on this page. The patching is done — so the reason this page existed is gone, and the only thing left to do is the thing it was always pointing at. Start Step 1. The plan was already good enough to carry you through Step 3 before any of this work, and Step 3 is where the actual transformation happens — everything else is perimeter. A plan that gets rewritten instead of executed is the most common failure mode in self-directed learning, and it looks exactly like productive work. This page is now a record, not a to-do list. Don't come back and improve it; go build the agent.
